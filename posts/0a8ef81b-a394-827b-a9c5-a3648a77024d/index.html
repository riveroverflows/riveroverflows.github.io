TL;DR
  • 일별 키 기반 실시간 랭킹은 자정마다 Cold Start에 부딪힌다.
  • 전략은 네 가지: Warm-Up Seeding, Read-time Merge, Sliding Window, Carry-Over.
  • 내 프로젝트에서는 Carry-Over를 선택했다. destination 덮어쓰기, TTL 소실, 블로킹 문제를 해결했고, 멱등성은 보류했다.

Redis ZSET 랭킹을 일별 키로 관리하면 자정에 조회 키가 바뀐다. 23:59:59까지 ranking:all:20260411을 읽던 API가 00:00:00부터 ranking:all:20260412를 읽는다. 새 키에는 데이터가 없고, 이전 키의 랭킹 데이터는 그대로 남는다. 이것이 Cold Start다.

Carry-Over는 네 전략 중 기존 구조를 가장 덜 변경한다. 오늘의 랭킹 데이터 일부를 내일 랭킹에 미리 반영하는 방식이다. Redis ZUNIONSTORE로 간단히 구현할 수 있을 줄 알았지만, destination 덮어쓰기, TTL 소실, Single Thread 블로킹, 멱등성 등 여러 문제를 마주했다.

1. 문제 정의: 실시간 랭킹의 Cold Start
#

Redis Sorted Set 기반 실시간 랭킹의 일반적인 구조는 대략 다음과 같다.

  • 자료 구조: Redis Sorted Set
  • 키 네이밍: ranking:all:yyyyMMdd 형태로 일 단위 분리
  • 점수 갱신: Kafka 이벤트를 소비하면서 ZINCRBY ranking:all:yyyyMMdd +score {productId}
  • TTL: 키에 일정 기간(예: 2~7일) TTL 적용
  • 조회: ZREVRANGE ranking:all:yyyyMMdd 0 N-1 WITHSCORES

이 구조를 택하는 순간 자연스럽게 “시간 경계"가 생긴다. ranking:all:20260411과 ranking:all:20260412는 완전히 분리된 키다. 00:00이 지나면 조회 대상이 후자로 바뀐다.

Cold Start란 무엇인가. 새로운 시간 경계(일/시간)가 시작되는 순간 해당 키가 비어 있거나 유의미한 수준의 데이터가 쌓이지 않아 사용자에게 빈 랭킹 또는 편향된 랭킹이 노출되는 현상을 말한다. 시간 축을 따라 대략 이런 모습이다.

  • 00:00:00: 자정이 지난다. 오늘 키는 아직 존재하지 않는다.
  • 00:00:03: 첫 구매/조회 이벤트가 도착하고 ZINCRBY가 오늘 키를 생성한다. 이 순간 “오늘의 1위"는 방금 들어온 그 상품이다.
  • 00:01:00: 수 건에서 수십 건의 이벤트가 쌓인다. 여전히 top-N 대비 극소수.
  • 01:00:00: 1시간치 데이터가 쌓인다. 전일 종료 시점(수만~수십만 건) 대비 1/24 수준.

이 현상이 잘 드러나지 않는 이유는 “데이터가 없는 시스템"과 외형상 구별이 어렵기 때문이다. 화면상 비거나, 몇 개만 노출된다. 하지만 구조는 완전히 다르다.

구분단순 “데이터 없음”일별 키 랭킹의 Cold Start
원인아직 서비스 초기이거나 트래픽이 없음서비스는 정상 운영 중이나 시간 경계를 넘은 직후
지속 시간영구적 또는 장기주기적 (매일 반복)
예측 가능성낮음100% 예측 가능 (스케줄된 현상)
과거 데이터없음바로 직전까지 충분히 존재

어제는 충분히 있었던 데이터가 00:00이 된 순간 구조적으로 접근 경로가 끊긴 것이 Cold Start의 본질이다. 데이터의 부재가 아니라 설계의 부작용이다.

운영 관점에서 이 현상은 단순한 UX 이슈 이상이다.

  • 사용자 경험: 자정~새벽 시간대에 홈의 “실시간 인기 상품” 섹션이 비거나, 운 좋게 몇 건 팔린 상품이 “오늘의 1위"로 올라가는 편향된 랭킹이 노출된다. 랭킹이 실제 선호도를 반영하지 못한다는 인상이 누적된다.
  • 운영: 새벽은 CS/장애 대응 인력이 가장 적은 시간대다. “인기 상품이 왜 이것만 뜨냐"는 문의가 들어오면 원인 분석과 해명 비용이 붙는다.
  • 비즈니스: 자정 직후 랜덤에 가까운 상품이 반복적으로 1위에 오르는 패턴은 랭킹 자체의 신뢰도에 대한 평판 리스크로 이어진다.

결국 Cold Start는 **“데이터가 없어서 발생하는 근본 문제"가 아니라 “키를 시간 경계로 쪼갠 설계 선택의 부작용”**이다. 해결책 역시 설계 수준에서의 트레이드오프 선택이 된다. 섹션 2에서는 이 트레이드오프를 네 방향으로 풀어 본다: 외부에서 심거나(Warm-Up), 조회 시점에 합치거나(Read-time Merge), 시간 경계 자체를 없애거나(Sliding Window), 전일 데이터를 미리 옮기거나(Carry-Over).

2. 해결책들
#

Cold Start의 원인이 “시간 경계 쪼개기의 부작용"이라면 해법도 결국 설계 수준의 선택이 된다. 본 섹션은 Carry-Over 외의 세 가지 대표 접근을 카탈로그처럼 훑는다. 각 항목은 원리, 간단한 예시, 장단점, 적합한 상황 순으로 정리했다. 본 프로젝트가 직접 구현한 것은 Carry-Over뿐이므로, 나머지 셋은 의사코드 수준에서 소개한다.

2.1 Warm-Up Seeding: 외부 데이터로 초기값을 심는다
#

원리. 자정 직전 또는 직후에 배치 스케줄러가 DB/집계 시스템/추천 엔진의 결과를 “오늘 키"에 미리 주입한다. 사용자 입장에서는 자정에 이미 랭킹이 채워져 있는 상태로 시작하므로 Cold Start가 경험 차원에서 숨겨진다.

예시 (의사코드).

@Scheduled(cron = "0 55 23 * * *")
fun warmUpRanking() {
    val tomorrowKey = "ranking:all:${tomorrow().format("yyyyMMdd")}"

    // DB 또는 추천 시스템에서 초기 점수 소스 확보
    val seeds = statsRepository.findTopProductsFromLastNDays(days = 7, limit = 200)

    redis.pipelined {
        seeds.forEach { (productId, score) ->
            zadd(tomorrowKey, score, productId)
        }
        expire(tomorrowKey, TTL_SECONDS)
    }
}

Redis ZADD의 시간 복잡도는 원소당 \(O(\log N)\)이다1. pipeline으로 수백 건 단위 주입이라면 비용 측면에서 감당 가능한 범주다.

장단점.

  • 장점: 자정 직후 UX 차원에서 Cold Start가 드러나지 않는다. 시드 소스를 “최근 7일 집계”, “ML 추천 결과”, “수동 큐레이션” 등 자유롭게 고를 수 있어 비즈니스 의도를 직접 반영하기 쉽다.
  • 단점: 별도의 집계 배치 파이프라인이 필요하다. 실시간 이벤트 파이프라인 외에 운영해야 할 컴포넌트가 하나 더 생긴다. 시드가 하루 종일 점수에 영향을 주므로 새벽 시간대의 “시드 편향"이 오래 남는다. 그리고 시드 주입 실패 시 Cold Start가 다시 발생하므로, 배치 잡의 신뢰성이 랭킹 품질의 직접 의존이 된다.

적합한 상황. 자정 UX가 서비스의 핵심이고, 별도 추천/통계 시스템이 이미 운영 중이라 배치 파이프라인 구축 비용이 낮은 경우. “오늘 시작된 이벤트만 반영해야 한다"는 정책적 요구가 있는 경우(예: 선착순 이벤트 랭킹)에는 부적합하다.

Redis 공식 블로그의 이커머스 추천 관련 글은 BBC iPlayer가 개인화 서빙이 빠르게 되지 않을 때 “popular/trending items를 fallback으로 사용"한다고 소개한다2. 사전 계산된 인기 리스트를 실시간 경로의 보완재로 쓴다는 점에서 Warm-Up Seeding과 같은 계열의 사고방식이다.

2.2 Fallback / Read-time Merge: 조회 시점에 이전 키와 합친다
#

원리. 쓰기 경로는 건드리지 않는다. 조회 시점에 오늘 키가 비어 있거나 부족하면 어제 키를 대신(또는 병합)하여 응답한다. “없을 때만 쓰는 폴백"이라는 점에서 가장 직관적인 접근이다.

구현은 두 갈래다.

(a) Redis 레벨: 조회 요청이 들어올 때 임시 키에 ZUNIONSTORE를 돌리고 그 임시 키를 읽는다.

ZUNIONSTORE ranking:tmp:{reqId} 2 today yesterday WEIGHTS 1 0.5
ZREVRANGE ranking:tmp:{reqId} 0 19 WITHSCORES
EXPIRE ranking:tmp:{reqId} 10

(b) 애플리케이션 레벨: 두 키를 각각 읽어 코드에서 병합한다.

fun getTopRanking(limit: Int): List<RankingItem> {
    val today = redis.zRevRangeWithScores("ranking:all:$today", 0, limit - 1)
    if (today.size >= limit) return today.map { it.toItem() }

    val yesterday = redis.zRevRangeWithScores("ranking:all:$yesterday", 0, limit - 1)
    return (today + yesterday)
        .groupBy { it.member }
        .mapValues { (_, list) -> list.sumOf { it.score } }
        .entries
        .sortedByDescending { it.value }
        .take(limit)
        .map { RankingItem(it.key, it.value) }
}

두 방식은 비용이 붙는 위치가 다르다.

기준(a) Redis ZUNIONSTORE(b) Application merge
비용 위치Redis애플리케이션
조회 1건당 비용\(O(N)+O(M \log M)\) + 임시 키 쓰기/삭제\(O(\log N + M)\) × 2 + 네트워크 왕복
결과 정확도전체 원소 union 후 top-K (정확)두 집합에서 각각 top-K를 가져와 병합 (근사)

(b)의 근사 이슈를 조금 더 풀면: “오늘 상위 K + 어제 상위 K"에 포함되지 않은 상품이 실제 병합 결과의 top-K에 들어야 했을 수 있다. 정확도가 중요하면 K보다 큰 K’(예: 3K)로 여유 있게 가져와 병합하고, 최종적으로 K개만 자르는 보정이 필요하다.

장단점.

  • 장점: 쓰기 경로에 손을 대지 않는다. 레거시 구조에 패치성으로 Cold Start 완화를 얹기 좋다. 자정 근처에만 이전 키를 참조하는 “조건부 fallback"으로 만들면 평상시 비용은 없다.
  • 단점: 조회 시점 비용이 매 요청마다 발생한다. (a)는 매 조회마다 ZUNIONSTORE를 돌리는 구조라 3.3.3에서 다룬 Single Thread 블로킹 리스크가 그대로 재연된다. (b)는 top-K 병합의 근사 이슈를 정확도와 비용 사이에서 조율해야 한다.

적합한 상황. 이벤트가 적은 새벽 몇 시간 동안만 fallback이 필요하고 조회 QPS가 낮거나 중간 수준인 경우. 쓰기 파이프라인을 수정하기 어려운 레거시 구조에 Cold Start 완화를 얹고 싶은 경우.

Stack Overflow의 한 답변은 7일치 일별 키를 ZUNIONSTORE로 합쳐 “지난 7일 랭킹"을 구하는 패턴을 보여 준다3. 시간축 병합이라는 관점에서 Read-time Merge의 전형이다.

2.3 Sliding Window: 시간 경계를 고정하지 않는다
#

원리. 고정된 일별 키를 쓰지 않고 “현재 시점에서 과거 T 시간 동안의 이벤트만 카운트"하는 구조로 전환한다. 시간축이 “현재 시점을 기준으로 뒤로 T 만큼"으로 바뀌므로 매일 자정마다 반복되는 주기적 Cold Start는 회피된다. 단, 시스템 최초 오픈, 대규모 장애 복구, 신규 상품 대량 등록 직후처럼 데이터 자체가 없는 근본적 Cold Start는 여전히 존재한다.

Redis에서 흔히 쓰이는 둘을 소개한다.

(1) 복수 버킷 + rolling: 시간을 1시간/1분 단위 버킷으로 쪼갠 후 현재 시점을 기준으로 최근 N개 버킷을 합산한다.

# 쓰기 (1시간 버킷)
ZINCRBY ranking:bucket:{now // 3600} 1 {productId}
EXPIRE ranking:bucket:{now // 3600} {retention}

# 조회 (최근 24개 버킷 = 24시간)
ZUNIONSTORE tmp 24 ranking:bucket:{b0} ... ranking:bucket:{b23}
ZREVRANGE tmp 0 N-1 WITHSCORES

ZINCRBY 기반 상품별 집계를 유지할 수 있다는 점이 장점이다. 단점은 버킷 경계에서 정밀도 손실(최대 1시간)이 발생하고, 조회 시 여러 버킷에 걸친 ZUNIONSTORE가 실행되므로 버킷 수가 많아질수록 비용이 누적된다는 점이다.

(2) ZSET + timestamp 기반 만료: 이벤트 하나하나를 Sorted Set의 멤버로 저장하고 점수는 timestamp로 삼는다. 조회 시 ZREMRANGEBYSCORE로 T 이전 이벤트를 제거한다.

# 쓰기
ZADD ranking:events {timestamp} "{productId}:{eventId}"
ZREMRANGEBYSCORE ranking:events -inf ({timestamp - T})

# 조회 (상품별 카운트)
ZRANGE ranking:events {timestamp - T} +inf BYSCORE

정확한 sliding window를 만들 수 있지만, 멤버가 개별 이벤트라서 메모리 사용량이 이벤트 수에 비례한다. 하루 수백만 건이면 수백 MB~GB를 쓴다. 상품별 집계도 애플리케이션에서 후처리해야 하므로 ZINCRBY 기반 집계의 이점이 사라진다.

장단점.

  • 장점: 매일 자정마다 반복되는 주기적 Cold Start 자체가 존재하지 않는다. 시간 경계가 애초에 부자연스러운 도메인(rate limiter, 실시간 metrics)에서는 자연스러운 설계다.
  • 단점: 셋 중 구현 복잡도가 가장 크다. 쓰기/조회/정리 경로가 모두 영향을 받는 구조적 전환이다. 근본적 Cold Start는 여전히 남는다. 메모리 프로파일과 비용 구조가 일별 키 구조와 다르고, 예측하기도 더 어렵다.

적합한 상황. 일별 경계가 애초에 비즈니스 의미를 갖지 않는 도메인. 처음부터 Sliding Window로 설계를 시작한 경우.

참고로: 이커머스 랭킹의 메인 전략 사례는 리서치 범위에서 확인되지 않았다. Sliding Window를 rate limiter나 실시간 metrics 용도로 쓴 자료는 풍부하지만, 유명 이커머스 기업이 상품 랭킹의 메인 전략으로 채택한 공식 사례는 본 리서치 범위 안에서 확인되지 않았다. 랭킹 도메인에서는 “일 단위 또는 기간 집계 + fallback/carry-over"가 일반적이고, Sliding Window는 보조적으로 결합되는 경향이 있다는 정도의 인상이다.

3. 나의 선택: Carry-Over
#

3.1 왜 Carry-Over였는가
#

네 가지 해결책 중 Carry-Over를 메인 전략으로 삼은 이유는 “기존 구조에 가장 적게 손대면서 시도할 수 있다"는 점이었다. 다른 전략이 부적합하다는 뜻이 아니라, 주어진 제약 안에서 Carry-Over의 비용 함수가 가장 납득 가능했다는 뜻이다.

  • A. Warm-Up Seeding: 시드의 출처가 별도로 필요하다. 추천 시스템의 출력이든, 집계 배치 결과든, “매일 만들어 주는 무언가"가 전제된다. 현재 프로젝트에는 별도의 추천 파이프라인이 없고, 랭킹의 소스는 Kafka 이벤트뿐이다. 배치를 추가한다는 것은 운영해야 할 컴포넌트가 하나 더 늘어난다는 의미다.
  • B. Read-time Merge: 쓰기 경로는 그대로 두고 조회 시점에 두 키를 합친다. 구현은 가장 간결하지만 매 조회마다 ZUNIONSTORE 또는 애플리케이션 레벨 병합이 실행된다. 랭킹은 홈 화면에서 자주 노출되는 지면이라 조회 QPS가 누적될 가능성이 높고, 조회당 비용이 쌓이는 구조의 지속 가능성을 예단하기는 어려웠다.
  • C. Sliding Window: 일별 키 경계 자체를 없애는 구조적 전환이다. 쓰기 경로, 조회 경로, 메모리 프로파일 세 축이 모두 바뀐다. 이미 일별 키로 파이프라인을 구축한 상황에서 전면 전환의 부담이 컸다.
  • D. Carry-Over: 일별 키 구조를 그대로 두고 스케줄러 하나를 추가하면 된다. 가장 침습이 적다. 트레이드오프는 자정 근처의 원자성·멱등성·블로킹 이슈로 옮겨 가는데, 카탈로그 규모가 크지 않은 현재 상황에서는 수용 가능한 범주였다.

다만 이것이 영구적으로 옳다는 뜻은 아니다. 카탈로그가 수십만~수백만 단위로 커지면 ZUNIONSTORE의 블로킹이 체감되기 시작하고 (3.3.3 참고), 조회 패턴이 바뀌면 B로 보강할지 C로 전면 전환할지 재검토 대상이 된다. 아래 하위 섹션들은 Carry-Over가 완벽하다는 주장이 아니라, Carry-Over를 선택했을 때 의식해야 하는 동작 원리와 위험 요소에 대한 정리다.

3.2 기본 동작: 어제 랭킹 일부를 내일 랭킹에 반영한다
#

Carry-Over의 아이디어는 단순하다. 자정 직전에 스케줄러가 전일 키의 점수 일부(예: 10%)를 오늘 키에 미리 주입한다. 전체가 아니라 일부인 이유는 “오늘"이라는 의미를 지키기 위함이다. 오늘 쌓이는 이벤트는 가중치 1.0으로 누적되는 동안, 어제의 영향은 상대적으로 희석된다.

Sorted Set 간 가중치 합산을 Redis가 기본 지원하는 내장 명령이 ZUNIONSTORE다4. 공식 문서의 시간 복잡도 기술은 다음과 같다.

O(N)+O(M log(M)) with N being the sum of the sizes of the input sorted sets, and M being the number of elements in the resulting sorted set.

  • N: 입력 sorted set들의 크기의 합
  • M: 결과 sorted set의 원소 수

그리고 WEIGHTS 옵션으로 각 입력 집합의 점수에 배수를 곱할 수 있다. 예를 들어 ZUNIONSTORE dest 1 source WEIGHTS 0.1은 source의 모든 점수에 0.1을 곱해 dest에 저장한다.

본 프로젝트에서 이 로직을 캡슐화한 스케줄러는 다음과 같다.

@Component
class RankingCarryOverScheduler(
    private val productRankingRepository: ProductRankingRepository,
) {
    private val log = LoggerFactory.getLogger(javaClass)

    @Scheduled(cron = "0 50 23 * * *", zone = "Asia/Seoul")
    fun execute() {
        runCarryOver()
    }

    fun runCarryOver() {
        val today = LocalDate.now(ZoneId.of("Asia/Seoul"))
        val tomorrow = today.plusDays(1)

        runCatching {
            if (!productRankingRepository.exists(today)) {
                log.info("Skip carry-over. No ranking data for today={}.", today)
                return
            }
            productRankingRepository.carryOver(today, tomorrow, CARRY_OVER_WEIGHT)
            log.info("Carry-over completed. source={}, destination={}, weight={}", today, tomorrow, CARRY_OVER_WEIGHT)
        }.onFailure { e ->
            log.warn("Failed to execute carry-over. today={}", today, e)
        }
    }

    companion object {
        const val CARRY_OVER_WEIGHT = 0.1
    }
}

23:50(Asia/Seoul)에 실행되고, 가중치 0.1을 사용한다. 두 값 모두 과제 스펙의 예시 값을 그대로 따랐다. 엔지니어가 “이 값이 맞다"고 주장할 자리가 아니라 PM/DA가 운영 데이터를 보며 결정할 영역이다. 전체가 runCatching으로 감싸져 있어 예외가 발생해도 프로세스는 살아남고, 실패 시 다음 날 자연 리셋에 의존한다. 바꿔 말하면 이 스케줄러 한 번의 실패를 시스템 차원에서 복구할 장치는 없다.

그런데 공식 문서를 그대로 따른 한 줄(ZUNIONSTORE tomorrow 1 today WEIGHTS 0.1)만으로는 이 스케줄러가 안전하게 동작하지 않는다. 이 섹션의 나머지는 “왜 그런가"에 대한 기록이다.

3.3 실제로 부딪힌 세 가지 문제
#

3.3.1 destination 덮어쓰기: 먼저 도착한 데이터가 지워진다
#

Redis ZUNIONSTORE 공식 문서는 destination 처리 방식을 정확히 한 줄로 기술한다4.

If destination already exists, it is overwritten.

이 문구가 문제의 전부다. ZUNIONSTORE tomorrow 1 today WEIGHTS 0.1을 실행하면 tomorrow 키에 기존에 어떤 값이 있었든 전부 지워지고 today × 0.1로 교체된다.

스케줄러가 정확히 23:50에 실행되는 한 이 문제는 드러나지 않는다. 그 시점에 내일 키는 존재하지 않으므로 덮어쓸 것도 없다. 문제가 드러나는 시나리오는 따로 있다.

  • 스케줄러가 조금 늦게 실행되는 경우: 00:00:30에 실행된다면 그 30초 사이에 실시간 이벤트가 내일 키에 몇 건 쌓여 있을 수 있다. ZUNIONSTORE가 이들을 덮어쓴다.
  • 이벤트 consumer lag이 자정 근처에 큰 경우: 23:50에 발행된 이벤트가 00:02에 소비되어 이미 내일 키에 기록된 상태에서 carry-over가 실행되면 같은 문제가 생긴다.
  • 별도 시드 배치와 공존하는 경우: Warm-Up Seeding을 병행한다면 실행 순서에 따라 둘 중 하나가 지워진다.

첫 번째 시나리오는 프로젝트 운영에서 실제로 가능한 경로다. cron 자체는 안정적이지만 스케줄러 호스트의 GC나 배포 롤링 시점과 겹치면 몇 초~수십 초 밀릴 수 있다. 이 가능성을 무시하면 “자정 직후 몇 건만 있어야 할 랭킹이 완전히 비어 있다"는 류의 미묘한 버그가 발생한다.

해법은 destination을 입력 집합에도 포함시키는 트릭이다. 가중치 1을 줘서 기존 dest의 점수를 보존하면서 source의 점수에 0.1을 곱해 더한다.

ZUNIONSTORE dest 2 dest source WEIGHTS 1 0.1

본 프로젝트의 carryOver 구현은 dest 키 존재 여부에 따라 분기한다.

override fun carryOver(
    sourceDate: LocalDate,
    destinationDate: LocalDate,
    weight: Double,
) {
    val sourceKey = buildKey(sourceDate)
    val destKey = buildKey(destinationDate)
    val destExists = redisTemplate.hasKey(destKey) == true

    if (destExists) {
        redisTemplate.opsForZSet().unionAndStore(destKey, listOf(sourceKey), destKey, Aggregate.SUM, Weights.of(1.0, weight))
    } else {
        redisTemplate.opsForZSet().unionAndStore(sourceKey, emptyList(), destKey, Aggregate.SUM, Weights.of(weight))
    }
    redisTemplate.expire(destKey, TTL_DAYS, TimeUnit.DAYS)
}

dest가 존재할 때만 self-union을 수행하고, 존재하지 않으면 단순한 one-way union으로 비용을 아낀다. dest가 비어 있는 흔한 경우에 불필요한 self-union 오버헤드를 피하는 소소한 최적화다.

유의: 이것은 공식 계약이 아니다. destination을 입력 집합에 포함하는 패턴은 Redis 공식 문서에 허용도 금지도 되어 있지 않다. Stack Overflow에서 Redis 소스의 zunionInterDiffGenericCommand 함수를 읽은 Lior Kogan의 답변에 따르면, Redis는 이 케이스를 특별히 최적화하지도, 거부하지도 않는다5. 결과적으로 “소스코드 동작상 안전한 관행” 수준에서 성립할 뿐 “공식 권장"이 아니다. Redis major 버전을 업그레이드할 때는 해당 버전에서의 실제 동작을 직접 확인하는 회귀 테스트가 필요할 수 있다.

3.3.2 TTL 소실: *STORE는 기존 TTL을 지운다
#

두 번째 문제는 공식 문서에 훨씬 명시적으로 쓰여 있다. Redis EXPIRE 문서의 기술은 다음과 같다6.

The timeout will only be cleared by commands that delete or overwrite the contents of the key, including DEL, SET, GETSET and all the *STORE commands.

ZUNIONSTORE, ZINTERSTORE, SUNIONSTORE 같은 *STORE 계열 명령은 모두 destination 키의 TTL을 제거한다. 앞의 3.3.1에서 수정한 carry-over 로직을 거친 tomorrow 키가 기존에 TTL을 가지고 있었더라도 ZUNIONSTORE 이후에는 TTL이 없는 상태가 된다. 방치하면 키가 메모리에 영원히 머무른다.

해법은 단순하다. ZUNIONSTORE 이후에 명시적으로 EXPIRE를 다시 호출한다. 위 코드에서 이미 등장한 마지막 두 줄이다.

redisTemplate.opsForZSet().unionAndStore(/* ... */)
redisTemplate.expire(destKey, TTL_DAYS, TimeUnit.DAYS)

두 줄이 한 세트다. 한 줄을 빠뜨리는 순간 실패의 성격이 “데이터 손실"이 아니라 **“조용히 진행되는 메모리 누수”**가 된다. 이쪽이 더 까다롭다. 데이터가 틀리면 테스트가 잡아내지만, TTL이 빠진 키는 기능상 정상으로 보이고 TTL key == -1을 모니터링하기 전까지 드러나지 않는다.

또 하나 의식해야 할 점은 unionAndStore와 expire가 별개의 명령이라는 것이다. 두 명령 사이에 틈이 있다. 프로세스가 unionAndStore 직후 expire 이전에 죽으면 tomorrow 키는 영속 상태로 남는다. 완전한 원자성을 원한다면 Lua 스크립트나 MULTI/EXEC로 두 명령을 원자 블록으로 묶어야 한다. 본 프로젝트는 이 틈을 수용하되 운영 시 TTL ranking:all:* == -1을 모니터링하는 후속 과제로 남겨두었다.

3.3.3 Single Thread: 원자성과 블로킹의 양면
#

Redis의 실행 모델은 공식 Diagnosing latency issues 문서에 정리되어 있다7.

Redis uses a mostly single threaded design. This means that a single process serves all the client requests, using a technique called multiplexing. This means that Redis can serve a single request in every given moment, so all the requests are served sequentially.

이 단일 실행 모델은 양면성을 가진다.

ZUNIONSTORE가 실행되는 동안 다른 클라이언트 명령은 사이에 끼어들지 못한다. 3.3.1의 self-union 트릭이 안전하게 동작하는 것도 이 덕분이다. 중간 상태가 외부에 노출되지 않으므로 연산 결과는 항상 완전하다. 대신 같은 이유로 ZUNIONSTORE가 실행되는 \(O(N)+O(M \log M)\) 시간 동안 다른 모든 명령이 대기한다. 공식 문서는 이렇게 덧붙인다7.

A consequence of being single thread is that when a request is slow to serve all the other clients will wait for this request to be served.

N은 어제 키의 크기(당일 누적 고유 상품 수)와 대략 일치한다. 카탈로그 규모가 수만~수십만 단위로 커지면 이 블로킹이 체감 가능한 수준으로 늘어날 수 있다.

구체 수치에 대한 유보: Redis 공식 문서에는 “카탈로그 N개일 때 ZUNIONSTORE가 몇 ms"라는 형태의 벤치마크가 없다. GitHub redis/redis 저장소의 issue #13929에서 memtier_benchmark로 50개 source key를 ZUNIONSTORE한 사례가 있고 약 230 ops/sec / 38ms latency 수준으로 보고되어 있지만8, 이 수치는 파이프라이닝과 병렬 접근이 섞인 throughput 관측이라 “단일 호출의 지연"으로 단정하기는 어렵다. 본인 카탈로그와 하드웨어에서 얼마가 걸리는지를 아는 유일한 방법은 운영 환경의 SLOWLOG GET으로 직접 관측하는 것이다9.

이 섹션에서 내릴 수 있는 결론은 단순하다. ZUNIONSTORE의 원자성은 고마운 성질이고, 그 대가로 받는 블로킹은 카탈로그가 커질수록 체감이 커진다. 단일 명령 지연은 운영 환경의 SLOWLOG로 추적해야 하며, 이 데이터가 쌓인 뒤에야 “Carry-Over를 언제까지 유지할 수 있는가"에 대한 판단이 가능해진다.

추가로, Redis 6의 I/O multithreading은 이 이야기에 영향을 주지 않는다. Redis 공식 블로그에 따르면 I/O threading은 socket read/write만 병렬화하고 명령 실행 자체는 여전히 단일 스레드다10. 버전을 6으로 올린다고 ZUNIONSTORE의 블로킹이 해소되지는 않는다.

3.4 멱등성: 미해결의 고백
#

앞의 세 문제는 “의식하고 처리하면 해결된다"는 범주였다. 멱등성은 성격이 다르다. 본 프로젝트는 의식했지만 해결을 보류했다.

문제의 시나리오는 간단하다. 스케줄러가 어떤 이유로든 두 번 실행되면 같은 transformation이 두 번 적용된다.

1회 실행: today ← today + (yesterday × 0.1)
2회 실행: today ← [today + (yesterday × 0.1)] + (yesterday × 0.1)
             = today + (yesterday × 0.2)

두 배의 carry-over가 쌓인 셈이다. 오늘의 순위가 어제의 영향을 의도보다 두 배로 받는다. 점수 값 자체는 Redis가 문제 없이 저장하지만, 의미가 망가진다.

두 번 실행되는 경로는 생각보다 많다.

  • 여러 인스턴스 동시 실행: 애플리케이션을 여러 대로 띄우면 각 인스턴스의 @Scheduled가 자정에 동시에 깨어난다.
  • 배포 롤링 중 겹침: 구 인스턴스가 종료되기 전에 신 인스턴스가 기동되는 창(window)에 자정이 들어오면 둘 다 실행한다.
  • 외부 스케줄러의 재시도: Kubernetes CronJob 등 외부 스케줄러가 장애 복구 후 재시도 정책으로 같은 잡을 다시 실행할 수 있다.

일반적인 해법은 Redis 분산 락 또는 센티넬 키다. Redis 공식 Distributed Locks 문서는 단일 인스턴스 락의 최소 형태를 다음과 같이 소개한다11.

SET resource_name my_random_value NX PX 30000

이 문구를 변형해 SET carry_over_done:20260412 1 NX EX 3600만 붙여도 “같은 날짜의 carry-over는 한 번만” 실행되는 효과가 생긴다. Redisson의 RLock을 쓰면 TTL 자동 연장(watchdog)까지 얻는다.

하지만 내 프로젝트에는 이 방법을 적용하지 않았다. 몇 가지 이유가 얽혀 있다.

  1. 현재 배포 토폴로지가 단일 인스턴스다. 자정에 @Scheduled가 두 번 깨어날 물리적 경로가 아직 없다.
  2. 이 선택이 영구하지 않다는 것을 알고 있다. 인스턴스가 늘거나 배포 롤링이 자정과 겹치는 설계가 들어오는 순간 무너지는 가정이다. 그 시점이 분산 락 도입의 트리거가 된다.
  3. 분산 락 도입은 그 자체로 또 다른 고민을 유발한다. 락 TTL을 얼마로 잡을지, 락 해제 실패 시 어떻게 복구할지, 락 획득 실패를 스케줄 누락으로 넘길 범위를 어디까지로 둘지. 이 결정들은 “carry-over 이상 동작을 실제로 관측한 적이 있는가"라는 운영 데이터가 쌓인 뒤에 내려야 근거를 가진다.

Redis 공식 문서도 단일 인스턴스 락에 대해 “a race condition from time to time is acceptable” 조건에서만 viable하다고 명시한다11. 센티넬 키 패턴은 정확히 말하면 exactly-once가 아니다. “중복 실행을 막는” 장치일 뿐 “정확히 한 번 실행됨"을 보장하지 않는다. 센티넬을 세운 직후 프로세스가 죽으면 당일 carry-over는 스킵된 채로 남는다. 랭킹이 “가끔 한 번 놓치는 것"이 치명적이지 않다는 도메인 특성 덕분에 이 수용 조건에 부합한다.

결론은 “지금은 안 넣었다"이고, 그 이유는 “현재 토폴로지에서 중복 실행 확률이 0에 가깝고, 도입의 구체 설정을 운영 데이터 없이 내릴 수 없다"는 것이다. 이런 조건부 타협은 문서로 남겨 두는 편이 좋다. 나중에 이 코드를 본 사람이 “왜 락이 없지?“를 “몰라서 빠뜨린 것"이 아니라 “당시의 판단"으로 읽을 수 있어야, 상황이 바뀌었을 때 가정을 재검토할 수 있다.

4. 정리
#

어떤 상황에서 어떤 선택이 적합할 지 정리했다. 각 항목은 판단의 기준이지 정답이 아니다.

  • 자정 UX가 가장 중요하고 별도 추천 인프라가 있다 → A. Warm-Up Seeding. 시드 소스만 구하면 사용자 경험 차원에서 Cold Start를 숨길 수 있다.
  • 기존 구조 변경 최소화 + 조회 QPS가 낮거나 중간 → B. Read-time Merge. 쓰기 경로를 건드리지 않고 조회 시점에 fallback을 얹는 쪽이 비용 대비 효과가 좋다.
  • 시간 경계 자체가 부자연스러운 도메인 → C. Sliding Window. 랭킹 도메인에서 메인 전략으로 쓴 유명 사례는 확인되지 않았지만, 도메인이 애초에 “시간 경계 없는” 성질이라면 자연스러운 선택이다.
  • 어제 데이터의 연속성을 “조금” 유지하면서 오늘을 채우고 싶음 + 카탈로그 규모 중간 이하 → D. Carry-Over. 기존 일별 키 구조를 그대로 유지할 수 있고 스케줄러 하나 추가로 끝난다. 단, 3.3과 3.4에서 다룬 함정을 의식해야 한다.

하이브리드가 실무의 기본이다. 네 가지 전략은 서로 배타적이지 않다. 실무에서는 조합이 훨씬 흔하다.

  • A + D: 시드로 초기값을 심고, 매일 추가로 어제 데이터의 일부를 주입해 연속성을 보강한다. 둘 다 같은 키에 쓰므로 실행 순서와 멱등성이 더 중요해진다.
  • B + D: Carry-Over로 웜업하되 실행 실패 시 조회 시점 fallback으로 보완한다. 신뢰성은 가장 높은 조합이다.
  • B (평시) + A (특정 날만): 평일은 실시간 이벤트가 충분하므로 조회 fallback만 두고, 주말/휴일 자정에만 warm-up seeding을 추가 실행한다.

본 프로젝트는 D를 기반으로 하고, 운영 데이터가 쌓이면 B로 2단 방어선을 보강하는 쪽을 염두에 두었다. 카탈로그 규모가 커지거나 SLOWLOG가 자정 근처에 ZUNIONSTORE를 반복해 기록하기 시작하면 C로의 전환 검토가 시작된다.

어떤 전략도 최종 답은 아니다. 운영 환경에서 관측된 신호가 쌓일 때마다 이전 결정의 가정이 흔들릴 수 있고, 그 순간이 재평가의 시점이다.
