TL;DR

결제가 실패하면 주문을 무조건 롤백해야 할까?
#

이번 라운드 과제는 외부 PG 시스템과 연동하여 결제 기능을 구현하는 것이었다. PG Simulator는 비동기 결제를 제공하는데, 결제를 요청하면 결과가 바로 오는 게 아니라 콜백으로 나중에 온다.

요청 성공률은 60%. 10건 중 4건은 요청 자체가 실패한다. 응답 지연은 100~500ms. 타임아웃, 네트워크 단절, 콜백 유실까지 고려하면 “정상 흐름"보다 “실패 흐름"이 더 다양한 환경이다.

처음에는 단순하게 생각했다. 결제 요청 보내고, 성공하면 주문 확정, 실패하면 롤백. @Transactional로 묶으면 되지 않을까?

@Transactional의 한계: PG 결제는 롤백되지 않는다
#

이전 글에서 synchronized + @Transactional이 안 되는 걸 경험했다. 이번에는 @Transactional의 다른 한계를 만났다.

@Transactional 안에서 PG를 호출하면 이런 일이 벌어진다:

@Transactional 시작
  ├── 주문 상태를 PAYMENT_PENDING으로 변경
  ├── PG에 결제 요청 (HTTP 호출, 100~500ms)  ← 이 동안 DB 커넥션 점유
  ├── PG 결제 성공!
  ├── 주문 상태 갱신
  └── DB 커밋 실패  ← 여기서 터지면?
@Transactional 종료 (롤백)

@Transactional은 내부 DB만 롤백한다. PG에서 이미 승인된 결제를 취소하지 않는다. 결과: 돈은 빠졌는데 주문은 없다.

그래서 트랜잭션을 분리해야 한다:

[트랜잭션 1] Payment 레코드 생성 (PENDING) + Order 검증 → 커밋
[트랜잭션 밖] PG 호출
[트랜잭션 2] PG 응답에 따라 상태 갱신 → 커밋

PG는 트랜잭션 밖에서 호출한다. 실제 코드에서는 TransactionTemplate으로 명시적으로 경계를 잡았다:

fun create(command: PaymentCreateCommand): PaymentCreateResult {
    // 1. Circuit Breaker 사전 체크 — PG가 장애 중이면 Payment를 만들지도 않는다
    if (!pgPaymentPort.isAvailable()) {
        throw CoreException(ErrorType.PG_CIRCUIT_OPEN)
    }

    // 2. 트랜잭션 안에서 Payment 생성 + 멱등성 검증
    val txResult = transactionTemplate.execute {
        createPaymentInTransaction(command, idempotencyKey, fingerprint)
    }!!

    // 3. 트랜잭션 밖에서 PG 호출
    val pgResponse = pgPaymentPort.requestPayment(pgRequest)

    // 4. PG 응답에 따라 상태 전이
    val payment = when (pgResponse) {
        is PgPaymentResponse.Accepted -> saved.updateTransactionKey(pgResponse.transactionKey)
        is PgPaymentResponse.ImmediateFailure -> saved.fail(pgResponse.reasonCode)
        is PgPaymentResponse.Timeout -> saved.applyTimeoutFallback()
        is PgPaymentResponse.CircuitOpen -> { /* 보상 처리 */ }
    }
    paymentRepository.save(payment)
}

여기서 다음 질문이 떠올랐다. PG 응답이 타임아웃이면, 그건 “실패"인가?

성공도 실패도 아닌 “모른다”
#

로컬 메서드 호출은 성공 아니면 실패, 두 가지다. 하지만 외부 시스템 호출은 세 가지다:

  • 성공: PG가 정상 응답을 줌
  • 실패: PG가 에러를 반환함 (한도 초과, 잘못된 카드 등)
  • 모른다: 타임아웃, 네트워크 단절, 응답 유실

이 “모른다"가 가장 신경 쓰이는 부분이었다.

sequenceDiagram
    participant M as 가맹점
    participant PG as PG

    M->>PG: 결제 요청 (t=0s)
    Note over PG: 처리 중...
    Note over M: 타임아웃! (t=0.6s)
    M->>M: "실패로 처리하자" ← 위험!
    Note over PG: 승인 완료! (t=1s)
    PG-->>M: 콜백 전송
    Note over M: 이미 실패 처리했는데?

가맹점은 “실패"로 처리했는데, PG에서는 실제로 결제가 됐다. 고객의 카드에서 돈이 빠졌지만 주문은 실패 처리되어 있다.

그래서 타임아웃이 발생하면 FAILED가 아니라 PENDING으로 둬야 한다. “아직 모르니까 나중에 확인하겠다"는 뜻이다.

이 원칙을 코드로 표현하면 이렇다:

// PG 응답을 sealed interface로 표현
sealed interface PgPaymentResponse {
    data class Accepted(val transactionKey: String) : PgPaymentResponse
    data class ImmediateFailure(val reasonCode: PaymentReasonCode) : PgPaymentResponse
    data object Timeout : PgPaymentResponse
    data object CircuitOpen : PgPaymentResponse
}

예외를 던지는 대신 sealed interface로 모든 경우를 명시적으로 표현했다. 호출하는 쪽에서 when으로 각 경우를 빠짐없이 처리하게 된다.

Payment 도메인도 이 원칙을 반영한다:

class Payment private constructor(/* ... */) {

    fun succeed(transactionKey: String): Payment {
        if (status != Status.PENDING) throw CoreException(ErrorType.PAYMENT_INVALID_STATUS_TRANSITION)
        return Payment(/* 기존 값 유지, status = SUCCESS, transactionKey = transactionKey */)
    }

    fun fail(reasonCode: PaymentReasonCode): Payment {
        if (status != Status.PENDING) throw CoreException(ErrorType.PAYMENT_INVALID_STATUS_TRANSITION)
        return Payment(/* 기존 값 유지, status = FAILED, reasonCode = reasonCode */)
    }

    fun applyTimeoutFallback(): Payment {
        // 상태는 PENDING 유지, "아직 모른다"는 사실만 기록
        return Payment(/* 기존 값 유지, reasonCode = TIMEOUT_UNCERTAIN */)
    }

    enum class Status { PENDING, SUCCESS, FAILED }
}

상태 전이는 단방향이다. PENDING에서만 SUCCESS나 FAILED로 갈 수 있고, 역방향은 불가능하다. 이 규칙이 중복 콜백이나 동시 복구 시도에서도 상태가 꼬이지 않는 구조를 만들어준다.

시스템을 보호하는 3가지 패턴
#

PG의 요청 성공률이 60%다. 타임아웃 없이 매번 기다리면 스레드가 고갈되고, 장애가 전체 시스템으로 번진다. 세 가지 패턴으로 이걸 막았다.

Timeout: 얼마나 기다릴 것인가
#

pg:
  connect-timeout-ms: 200    # TCP 연결 수립 타임아웃
  timeout:
    overall-ms: 600          # 전체 요청 타임아웃 (하드 캡)

connect-timeout은 연결 자체가 안 될 때 빠르게 포기하는 값이고, overall-timeout은 연결부터 응답까지 전체를 자르는 하드 캡이다. PG 응답 지연이 100~500ms이니까, 600ms면 정상 응답은 대부분 통과시키면서 지연된 요청은 빠르게 자른다.

Circuit Breaker: 계속 보낼 것인가
#

PG가 계속 실패하는데 매번 요청을 보내면 의미 없는 타임아웃만 반복된다. Circuit Breaker는 “더 이상 보내지 않겠다"는 결정을 자동으로 내린다.

resilience4j:
  circuitbreaker:
    instances:
      pgPayment:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 10           # 최근 10건을 본다
        minimum-number-of-calls: 5        # 최소 5건은 쌓여야 판단
        failure-rate-threshold: 50        # 절반 이상 실패하면 OPEN
        slow-call-duration-threshold: 500ms  # 500ms 넘으면 "느린 호출"
        slow-call-rate-threshold: 60      # 느린 호출이 60% 넘으면 OPEN
        wait-duration-in-open-state: 30s  # 30초 후 시험 호출 허용
        permitted-number-of-calls-in-half-open-state: 3  # 3건만 시험

각 값을 정한 근거:

  • overall-timeout이 600ms인데 slow-call-duration-threshold를 500ms로 잡은 이유: 타임아웃 직전의 위험 구간을 조기 경보로 잡기 위해서다.
  • failure-rate-threshold를 50%로 잡은 이유: PG의 시스템 실패율이 약 40%인데, 비즈니스 예외(한도 초과, 잘못된 카드)를 ignoreExceptions로 제외하면 CB 기준 실패율이 약 49%가 된다. 50%면 정상 상태에서는 간신히 안 열리고, 진짜 장애일 때 열린다.

이 세 가지를 하나의 메서드로 조합했다:

private fun <T> executeProtected(block: () -> T): T {
    return circuitBreaker.executeCallable {
        CompletableFuture.supplyAsync(block, pgOutboundExecutor)
            .orTimeout(overallTimeoutMs, TimeUnit.MILLISECONDS)
            .join()
    }
}

Circuit Breaker가 호출을 감싸고, 내부에서 별도 스레드풀(pgOutboundExecutor)로 실행하고, orTimeout으로 전체 시간을 제한한다.

Fallback: 실패하면 어떻게 응답할 것인가
#

결제 Fallback에서 중요하다고 느낀 원칙이 있다. 성공으로 응답하지 않는다. 실패로 확정하지 않는다. PENDING으로 둔다.

상황상태 코드Payment 상태transactionKey
PG 정상 응답201PENDING있음
PG 타임아웃201PENDINGnull
PG 즉시 500201FAILEDnull
CB OPEN503미생성-

Retry는 왜 안 넣었나
#

이번 구현에서는 결제 요청 단계의 자동 Retry를 넣지 않았다. Retry는 실패를 즉시 만회하려는 전략이고, 이번에 다룬 콜백/폴링/배치는 실패를 인정하고 나중에 수렴시키는 전략이다. 둘은 방향이 다르고, 이번에는 후자에 먼저 집중하고 싶었다.

만약 Retry를 넣는다면, Circuit Breaker와의 조합 순서에 주의해야 한다. 궁금해서 별도 프로젝트에서 직접 테스트해봤다. Resilience4j의 기본 Aspect Order에서는 Retry가 바깥, CB가 안쪽에 위치한다.

// 기본 순서: Retry(바깥) → CB(안쪽)
@Retry(name = "pg")
@CircuitBreaker(name = "pg")
fun pay(): String {
    println("[PG 호출] 시도")
    throw RuntimeException("PG 서버 장애")
}

직접 돌려보면 차이가 바로 보인다. maxAttempts=3으로 설정하고 1건의 요청을 보내면:

기본 순서 (Retry 바깥, CB 안쪽):

[PG 호출] 시도
[PG 호출] 시도
[PG 호출] 시도
CB 실패 건수: 3    ← 1건의 요청인데 3건으로 부풀림

재시도할 때마다 CB에 각각 실패로 기록된다. 실패율이 부풀려져서 서킷이 필요 이상으로 빨리 열릴 수 있다.

Aspect Order를 바꿔 CB를 바깥으로 옮기면:

resilience4j:
  circuitbreaker:
    circuitBreakerAspectOrder: 1   # 작은 값 = 바깥
  retry:
    retryAspectOrder: 2             # 큰 값 = 안쪽

변경된 순서 (CB 바깥, Retry 안쪽):

[PG 호출] 시도
[PG 호출] 시도
[PG 호출] 시도
CB 실패 건수: 1    ← 재시도 전체가 1건으로 기록

재시도 3회를 포함한 전체가 CB 관점에서 하나의 호출로 기록된다. CB가 OPEN일 때는 Retry 자체가 실행되지 않는다.

복구는 어떻게?
#

PENDING 상태로 뒀으면, 언젠가는 최종 결과를 확인해야 한다. 콜백에만 의존하면 유실될 수 있으니, 3계층 복구 구조를 설계했다.

Layer 1: 콜백 (실시간)
  PG가 처리 완료 후 우리 서버로 POST → 상태 갱신

Layer 2: Eager Retry (준실시간)
  결제 생성 직후 5초, 30초, 2분 후 PG에 상태 조회 예약

Layer 3: Batch Sweep (정기)
  5분 주기로 오래된 PENDING 결제를 일괄 조회

각 계층은 이전 계층이 실패했을 때 동작하는 안전망이다. 콜백이 먼저 도착하면 나머지 재조회는 이미 terminal 상태인 걸 확인하고 건너뛴다.

사용자가 결제 상세를 조회할 때 read-repair도 수행한다. PENDING 상태의 결제를 조회하면 PG에 한 번 더 물어보고, 결과가 나왔으면 즉시 반영한다.

private fun readRepair(payment: Payment): Payment {
    if (payment.isTerminal || payment.transactionKey == null) return payment

    return try {
        val pgStatus = pgPaymentPort.queryPaymentStatus(payment.transactionKey, payment.userId)
        when (pgStatus.status.uppercase()) {
            "SUCCESS" -> {
                val succeeded = payment.succeed(pgStatus.transactionKey)
                paymentRepository.save(succeeded)
                orderRepository.save(order.confirm())
                succeeded
            }
            "FAILED" -> {
                val failed = payment.fail(PaymentReasonCode.fromPgReason(pgStatus.reason))
                paymentRepository.save(failed)
                failed
            }
            else -> payment  // 아직 PENDING이면 다음에 다시
        }
    } catch (e: Exception) {
        payment  // PG 조회 실패해도 기존 데이터를 반환 (fail-safe)
    }
}

WireMock으로 장애를 재현하다
#

타임아웃이나 서킷 브레이커는 정상 환경에서 재현하기 어렵다. WireMock으로 PG의 지연과 실패를 재현 가능하게 시뮬레이션했다.

타임아웃 재현
#

@Test
@DisplayName("PG 응답 지연 > overall timeout → Timeout 반환")
fun requestPayment_timeout() {
    wireMockServer.stubFor(
        post(urlPathEqualTo("/api/v1/payments"))
            .willReturn(
                aResponse()
                    .withFixedDelay(1000)   // 1초 지연 > 600ms 타임아웃
                    .withStatus(200)
            )
    )

    val response = adapter.requestPayment(pgRequest())

    assertThat(response).isEqualTo(PgPaymentResponse.Timeout)
}

600ms overall timeout을 설정한 상태에서 WireMock이 1초 지연을 주면, 예외 대신 PgPaymentResponse.Timeout이 반환된다.

Circuit Breaker 검증
#

@Test
@DisplayName("Circuit OPEN → PG 호출 없이 즉시 CircuitOpen 반환")
fun requestPayment_circuitOpen() {
    circuitBreakerRegistry.circuitBreaker("pgPayment").transitionToOpenState()

    val response = adapter.requestPayment(pgRequest())

    assertThat(response).isEqualTo(PgPaymentResponse.CircuitOpen)
    assertThat(wireMockServer.allServeEvents).isEmpty()  // PG 호출 자체가 없음
}

서킷이 OPEN이면 네트워크 요청 자체가 발생하지 않는다. wireMockServer.allServeEvents가 비어있는 걸로 확인할 수 있다.

동시성 테스트
#

같은 주문에 대해 PENDING 결제가 2건 이상 생기면 안 된다:

@Test
@DisplayName("5개 스레드 동시 요청 → PENDING Payment는 최대 1건")
fun create_concurrent_onlyOnePending() {
    val threadCount = 5
    val startLatch = CountDownLatch(1)
    val successCount = AtomicInteger(0)

    repeat(threadCount) {
        executor.submit {
            startLatch.await()  // 동시 시작
            try {
                paymentCreateUseCase.create(command(idempotencyKey = UUID.randomUUID().toString()))
                successCount.incrementAndGet()
            } catch (e: CoreException) { /* PAYMENT_ACTIVE_PENDING_EXISTS */ }
        }
    }
    startLatch.countDown()

    val pendingPayments = paymentRepository.findAllByOrderId(orderId)
        .filter { it.status == Payment.Status.PENDING }

    assertThat(pendingPayments).hasSize(1)
}

Order row lock(SELECT ... FOR UPDATE)으로 동시 요청 중 하나만 PENDING을 만들 수 있게 제어한다.

구현하면서 발견한 것들
#

비즈니스 예외와 시스템 예외는 다르다
#

PG Simulator의 전체 실패율은 높아 보이지만, 실제로 CB가 감지해야 할 건 시스템 실패뿐이다. “카드 한도 초과"는 PG가 정상적으로 처리한 결과이지 시스템 장애가 아니다.

요청 실패 (타임아웃, 500): 40% → CB에 기록
한도 초과: 12% → CB에서 제외
잘못된 카드: 6% → CB에서 제외

분리하지 않으면 정상 운영 중에도 서킷이 열릴 수 있다.

“이미 처리됨"은 에러가 아니다
#

콜백이 두 번 오거나, 폴링과 콜백이 동시에 도착할 수 있다. 이때 “이미 SUCCESS인 결제에 또 SUCCESS 콜백이 왔다"는 에러가 아니라 정상적인 중복이다.

fun handleCallback(command: PaymentCallbackCommand) {
    val payment = paymentRepository.findById(command.paymentId) ?: return
    if (payment.isTerminal) return  // 이미 처리됨 → no-op
    // ...
}

상태 머신이 단방향 전이만 허용하기 때문에, 중복 처리를 시도하더라도 무시된다.

상태 불일치는 버그가 아니다
#

PG에서 결제가 성공했는데 내부 주문이 아직 PENDING인 구간이 있다. 콜백이 아직 안 왔기 때문이다. 이건 버그가 아니라 분산 시스템에서 최종 일관성(Eventual Consistency)이 달성되기 전의 자연스러운 상태다. 콜백/폴링/배치가 이 불일치를 수렴시킨다.

“모른다"를 인정하는 시스템
#

외부 시스템과 연동할 때는 “성공 아니면 실패"라는 이분법이 통하지 않는다. 타임아웃이 발생해도 상대방은 이미 처리했을 수 있고, 콜백이 안 와도 결제는 완료됐을 수 있다. 이 “모른다” 상태를 시스템이 정직하게 표현하고, 나중에 수렴시키는 구조를 만드는 게 이번 라운드에서 가장 많이 고민한 부분이었다.

이전 글에서 “어떤 락을 쓸까보다 문제의 성격이 뭔가가 먼저"라고 썼는데, 이번에도 비슷한 결론에 도달했다. Timeout, Circuit Breaker, Fallback은 도구일 뿐이고, 진짜 중요한 건 외부 호출의 결과가 불확실할 때 시스템이 어떻게 행동할지를 먼저 정하는 것이었다.

상태 모델, 트랜잭션 경계, 복구 전략 — 이 세 가지를 먼저 설계하고 나니 어떤 패턴을 어디에 붙일지가 따라왔다. 반대로 패턴부터 붙이려고 했으면 아마 @CircuitBreaker 어노테이션만 달고 끝냈을 것이다.

Phase Review에서 발견한 보완점
#

구현을 마치고 Phase별로 리뷰했을 때 몇 가지 보완점을 발견했다.

  • 활성 PENDING 결제의 DB 제약: 코드에서는 findActiveByOrderId()로 체크하지만, DB 레벨의 unique 제약이 없어서 동시 요청 시 race condition이 남아있다. Order row lock으로 보완했지만, 저장 구조 자체에서 강제하는 것이 더 안전하다.
  • 상태 조회의 Resilience 보호: 결제 요청(requestPayment)에는 CB + timeout을 적용했지만, 상태 조회(queryPaymentStatus)에도 동일한 보호가 필요하다. 복구 경로가 느린 PG에 붙잡히면 복구 자체가 장애 원인이 될 수 있다.
  • Circuit Open race: CB 사전 체크(isAvailable())와 실제 PG 호출 사이에 서킷이 열릴 수 있다. 이 경우 이미 만들어진 Payment를 어떻게 처리할지 — 보상 삭제할지, 그대로 PENDING에 둘지 — 정책이 더 명확해야 한다.

이런 보완점들은 “구현이 끝났다"에서 멈추면 안 되고, 각 Phase에서 발생할 수 있는 경합과 누락을 하나씩 점검해야 한다는 걸 보여줬다.
