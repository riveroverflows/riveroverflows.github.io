TL;DR
  • 대기열 도입만으로는 시스템을 보호할 수 없다.
  • DB 부하를 제어하는 마이크로 배칭, 중복 실행을 막는 분산 락, 미사용 토큰을 회수하는 토큰 생명주기 관리가 필요하다.
  • 대기열 너머에 이 장치들이 하나의 파이프라인으로 연결되어야 시스템이 안전해진다.

대기열(Queue)을 도입하기로 결정했을 때, 대기열만 넣으면 모든 문제가 해결될 것이라 생각했다. “이제 트래픽이 아무리 몰려도 유저들을 순서대로 줄 세우기만 하면 시스템은 안전하겠지?“라고 믿었다. 하지만 실제 구현 후 테스트 서버에서 DB 커넥션 타임아웃이 발생하는 것을 보며 곧 깨달았다. 단순히 줄을 세우는 것과 시스템을 실제로 ‘보호’하는 것은 완전히 다른 문제라는 사실을 말이다.

대기열 전략 자체를 비교하기보다, Redis Sorted Set 기반의 대기열을 선택한 이후 시스템이 무너지지 않게 하려면 어떤 장치들이 맞물려야 하는지 직접 부딪히며 배운 경험을 정리해 보았다.

서론: 대기열을 도입하다
#

본격적인 문제 해결에 앞서, 우리가 구축한 최소한의 대기열 파이프라인을 살펴보자. Redis의 Sorted Set은 ZADD NX를 통해 시간 복잡도 \(O(\log N)\)으로 정렬된 상태를 유지하며 멤버를 추가할 수 있어 대기열 구현에 매우 적합하다.

flowchart TD
User -->|진입 요청| Interceptor{토큰 확인}
Interceptor -->|토큰 없음| Enter[대기열 진입\nZADD NX]
Enter --> Status[상태 조회\nZRANK / ZCARD]

    subgraph Scheduler [Background Job]
        S[QueueScheduler\n100ms 주기] --> Pop[유저 추출\nZPOPMIN]
        Pop --> Issue[토큰 발급\nSET EX 300]
    end
    
    Interceptor -->|토큰 유효| Origin[실제 주문 API 처리]
    Issue -.->|토큰 발급 완료| User

대기열에 들어온 유저는 자신의 순서를 기다리고, QueueScheduler는 주기적으로 상위 유저를 꺼내 ‘입장 토큰’을 발급한다. 유저는 이 토큰을 X-Entry-Token 헤더에 담아 주문 API를 호출하게 된다. 이 단순해 보이는 구조, 과연 무엇이 문제였을까?

본론: 대기열이 무너지는 지점들
#

1. DB 부하 집중
#

구현을 마치고 부하 테스트를 돌렸을 때 가장 먼저 마주한 문제는 **“줄을 세웠는데도 DB가 터진다”**는 것이었다. 여기서 나는 중요한 인식의 전환을 경험했다. 대기열이 있으니 순서대로 처리될 거라 생각했지만, 순서를 정하는 것과 한 번에 몇 명을 보낼지 제어하는 것은 별개의 문제였다.

한 번에 1000개를 꺼내면
#

만약 대기열에 10,000명이 있고, 스케줄러가 한 번에 1,000명씩 꺼내 토큰을 준다고 가정해 보자. 1,000명의 유저는 토큰을 받자마자 약속이라도 한 듯 동시에 주문 API를 호출할 것이다. 이는 대기열이 없을 때와 마찬가지로 Thundering Herd 현상을 발생시킨다. 대기열은 그저 폭발 시점을 조금 뒤로 미룬 방패에 불과했던 것이다.

배치 주기와 크기 산정
#

시스템을 실제로 보호하려면 DB가 감당할 수 있는 **처리량(Throughput)**을 보수적으로 산정하고, 이를 아주 잘게 쪼개서 흘려보내야 한다. 나는 다음과 같은 산식을 통해 타겟 TPS를 도출했다.

  • DB 커넥션 풀: 40개
  • 평균 처리 시간: ~130ms (재고 차감 + 쿠폰 검증 + 주문 저장 + 이벤트 발행, 실측 중앙값)
  • 안전 마진: 70% (예상치 못한 스파이크 대비)
  • Target TPS: \((40 / 0.13) \times 0.7 \approx 215\) TPS

초당 215명을 한꺼번에 푸는 것(1s 배치)과 100ms마다 21명씩 푸는 것(마이크로 배칭)은 DB 입장에서 완전히 다른 부하 곡선을 그린다.

배치 주기가 짧을수록 대기열의 흐름은 부드러워진다. 1초 배치는 유저에게 뚝뚝 끊기는 느낌을 주지만, 100ms 간격은 거의 실시간에 가까운 흐름을 만들면서도1 DB에 가해지는 순간 부하를 분산시킨다.

ZPOPMIN과 토큰 발급 사이의 갭
#

여기서 또 하나의 고민이 생겼다. Redis의 ZPOPMIN은 요소를 원자적으로 제거하면서 반환한다. 만약 스케줄러가 유저를 꺼낸 직후 토큰을 발급하기 전에 서버가 크래시되면, 해당 유저들은 대기열에서 사라졌지만 토큰은 받지 못한 ‘미아’ 상태가 된다.

이 문제는 ZPOPMIN과 토큰 발급이 별개의 연산이기 때문에 발생한다. 두 연산 사이의 갭에서 크래시가 일어나면 유저는 어디에도 속하지 못하게 된다. 나는 이 두 단계를 하나의 Lua Script로 묶어 원자적으로 처리하는 방식으로 해결했다.

local members = redis.call('ZPOPMIN', KEYS[1], ARGV[1])
local results = {}
local uuidIdx = 3
for i = 1, #members, 2 do
    local userId = members[i]
    local token = ARGV[uuidIdx]
    redis.call('SET', 'queue:entry-token:' .. userId, token, 'EX', ARGV[2])
    table.insert(results, userId)
    table.insert(results, token)
    uuidIdx = uuidIdx + 1
end
return results

Redis는 Lua Script를 단일 명령처럼 실행하므로, 대기열에서 유저를 꺼내는 것과 토큰을 발급하는 것이 항상 함께 일어난다. 스크립트가 실행되면 둘 다 완료되고, 실행 전에 크래시하면 둘 다 일어나지 않는다. ‘꺼냈는데 토큰은 없는’ 미아 상태가 구조적으로 발생하지 않는 것이다.

물론 이보다 더 견고한 방법도 있다. 3-Queue 모델(Pending → Processing → Completed) 은 각 단계를 별도 큐로 관리하면서, 처리가 완료된 후에만 유저를 삭제하는 방식이다. 하지만 현재 시스템에서는 Lua Script의 원자성만으로 충분한 신뢰성을 확보할 수 있다고 판단하여 도입하지 않았다.

2. 토큰 중복 발급
#

시스템 가용성을 위해 서버를 3대로 늘리자마자 예상치 못한 문제가 터졌다. 초당 215명을 내보내기로 했는데, 실제로는 21명 × 10회 × 3대 = 630명이 나가고 있었던 것이다. 각 서버의 QueueScheduler가 독립적으로 작동하며 각자 21명씩 유저를 풀고 있었기 때문이다.

이를 해결하기 위해 Redis 분산 락을 도입했다.

// QueueScheduler.kt 의 핵심 로직
@Scheduled(fixedDelayString = "\${queue.scheduler.fixed-delay:100}")
fun processQueue() {
    val lockValue = tryAcquireLock() ?: return
    try {
        val uuids = (1..BATCH_SIZE).map { UUID.randomUUID().toString() }
        val args = listOf(BATCH_SIZE.toString(), TOKEN_TTL_SECONDS) + uuids
        redisTemplate.execute(POP_AND_ISSUE_SCRIPT, listOf(WAITING_QUEUE_KEY), *args.toTypedArray())
    } finally {
        releaseLock(lockValue)
    }
}

private fun tryAcquireLock(): String? {
    val value = UUID.randomUUID().toString()
    val acquired = redisTemplate.opsForValue()
        .setIfAbsent(LOCK_KEY, value, LOCK_LEASE) == true
    return if (acquired) value else null
}

분산 락은 효율성(Efficiency), 정확성(Correctness) 두 가지 목적으로 나눠볼 수 있다2. 대기열 스케줄러는 중복 실행을 막아 시스템 부하를 방지하는 ‘효율성’의 성격이 강하다. 설령 아주 드문 확률로 락이 튀어 토큰이 조금 더 발급되더라도, 최종 인터셉터에서 토큰 유효성을 검증하므로 데이터 정합성이 깨지지는 않는다. 따라서 Redlock 같은 무거운 도구 대신, 단일 Redis를 이용한 SET NX EX로도 충분하다는 판단을 내렸다.

다만 순간적으로 계획보다 많은 유저가 유입되어 DB 부하가 일시적으로 높아질 가능성은 남아 있다. 이를 위해 앞서 Target TPS를 산정할 때 30%의 안전 마진을 확보해 둔 것이기도 하다. 또한 해제 시에는 자신이 획득한 락만 삭제하도록 Lua Script로 소유권을 검증한다. 단순 DEL로 해제하면 lease 만료 후 다른 인스턴스의 락까지 지워버릴 수 있기 때문이다.

3. 토큰 미사용
#

어렵게 발급한 토큰이 ‘유령 슬롯’이 되는 상황도 막아야 했다. 유저가 대기열을 뚫고 토큰을 받았는데 정작 주문 버튼을 누르지 않고 창을 닫아버리면, 그만큼 다른 유저들의 입장이 늦어지기 때문이다.

이 문제는 토큰의 생명주기를 세 단계로 나눠 관리하는 것으로 해결했다.

1단계: TTL로 만료 보장
#

토큰 발급 시 SET EX 300을 통해 5분 뒤 자동 만료되게 했다. 유저가 토큰을 받고 아무 행동도 하지 않더라도 슬롯은 5분 뒤에 반환된다.

2단계: 인터셉터는 검증만
#

주문 API에 도달했을 때, 인터셉터는 X-Entry-Token 헤더의 토큰이 유효한지 확인만 하고 삭제하지 않는다.

// EntryTokenInterceptor.kt
override fun preHandle(request: HttpServletRequest, ...): Boolean {
    if (request.method != "POST") return true

    val userId = userAuthenticateUseCase.authenticateAndGetId(loginId, password)
    val token = request.getHeader("X-Entry-Token")
        ?: throw CoreException(ErrorType.ENTRY_TOKEN_REQUIRED)

    if (!entryTokenValidationUseCase.validate(userId, token)) {
        throw CoreException(ErrorType.ENTRY_TOKEN_INVALID)
    }
    return true
}

처음에는 인터셉터에서 검증과 삭제를 동시에 처리했다. 하지만 이 방식에는 문제가 있었다. 인터셉터를 통과한 뒤 @Valid 검증 실패(400)나 DB 장애(500)가 발생하면, 토큰은 이미 삭제되었으므로 유저는 재시도할 수 없게 된다.

3단계: 주문 완료 후 삭제
#

토큰 삭제는 DB 트랜잭션이 커밋된 이후(AFTER_COMMIT)에 처리한다. 주문이 확실히 성공한 시점에서만 토큰을 소비하는 것이다.

// OrderCreatedEventListener.kt
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
fun handle(event: OrderCreatedEvent) {
    if (event.hasEntryToken) {
        runCatching { entryTokenRepository.delete(event.userId) }
            .onFailure { log.warn("Failed to delete entry token for userId={}", event.userId, it) }
    }
}

삭제에 실패하더라도 TTL이 안전망 역할을 한다. 5분 뒤면 토큰은 자연 만료되므로, 슬롯이 영구적으로 점유되는 일은 없다.

이 방식은 토큰이 삭제되기 전까지 같은 토큰으로 여러 요청이 통과할 수 있다는 트레이드오프가 있다. 하지만 대기열 토큰의 역할은 트래픽 제어이고, 중복 주문 방지는 idempotency key의 책임이므로 허용 가능한 범위라고 판단했다.

결론: 대기열 너머의 파이프라인
#

대기열을 구현하며 얻은 가장 큰 교훈은, 대기열이 단순한 ‘저장소’가 아니라 정교하게 설계된 파이프라인이어야 한다는 점이었다.

깨지는 지점증상해결 장치
한 번에 전부 풀어줌DB Thundering Herd마이크로 배칭 (100ms / 21명)
서버 수만큼 스케줄러 실행토큰 과다 발급분산 락 (SET NX EX)
토큰 발급 후 미방문처리량 정체 (‘유령 슬롯’)TTL + AFTER_COMMIT 삭제

Auto Scaling은 메트릭 수집부터 인스턴스 준비까지 최소 수 분이 걸리기 때문에 순간적인 트래픽 스파이크에는 늦다. 대기열은 그 공백을 메우는 역할을 한다.

줄을 세우는 것만으로는 부족하다. 그 줄이 어떻게 빠져나가고, 어떻게 소멸되는지까지 관리해야 비로소 시스템은 안전해진다.

  1. Jakob Nielsen, Response Times: The 3 Important Limits (1993) — 100ms 미만의 지연을 인간이 “즉각적"으로 느끼는 임계치로 제시. ↩︎

  2. Martin Kleppmann, How to do distributed locking (2016) — 분산 락의 목적을 효율성(efficiency)과 정확성(correctness)으로 구분하고, 각 목적에 따른 설계 기준을 제시한 글. ↩︎
