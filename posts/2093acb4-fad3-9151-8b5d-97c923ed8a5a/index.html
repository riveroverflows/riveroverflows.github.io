TL;DR
  • 대기열 도입만으로는 시스템을 보호할 수 없다.
  • DB를 지키는 마이크로 배칭(100ms 단위), 서버 분산 환경을 위한 분산 락, 유령 슬롯을 막는 토큰 생명주기 관리가 필요하다.
  • 이 장치들이 하나의 파이프라인으로 맞물려야 비로소 시스템이 안전해진다.

대기열(Queue)을 도입하기로 결정했을 때, 대기열만 넣으면 모든 문제가 해결될 것이라 생각했다. “이제 트래픽이 아무리 몰려도 유저들을 순서대로 줄 세우기만 하면 시스템은 안전하겠지?“라고 믿었다. 하지만 실제 구현 후 테스트 서버에서 DB 커넥션 타임아웃이 발생하는 것을 보며 곧 깨달았다. 단순히 줄을 세우는 것과 시스템을 실제로 ‘보호’하는 것은 완전히 다른 문제라는 사실을 말이다.

대기열 전략 자체를 비교하기보다, Redis Sorted Set 기반의 대기열을 선택한 이후 시스템이 무너지지 않게 하려면 어떤 장치들이 맞물려야 하는지 직접 부딪히며 배운 경험을 정리해 보았다.

1. Redis Sorted Set으로 줄을 세우다
#

본격적인 문제 해결에 앞서, 우리가 구축한 최소한의 대기열 파이프라인을 살펴보자. Redis의 Sorted Set은 ZADD NX를 통해 시간 복잡도 $O(\log N)$으로 정렬된 상태를 유지하며 멤버를 추가할 수 있어 대기열 구현에 매우 적합하다.

flowchart TD
    User -->|진입 요청| Interceptor{토큰 확인}
    Interceptor -->|토큰 없음| Enter[대기열 진입\nZADD NX]
    Enter --> Status[상태 조회\nZRANK / ZCARD]
    
    subgraph Scheduler [Background Job]
        S[QueueScheduler\n100ms 주기] --> Pop[유저 추출\nZPOPMIN]
        Pop --> Issue[토큰 발급\nSET EX 300]
    end
    
    Interceptor -->|토큰 유효| Origin[실제 주문 API 처리]
    Issue -.->|토큰 발급 완료| User

대기열에 들어온 유저는 자신의 순서를 기다리고, QueueScheduler는 주기적으로 상위 유저를 꺼내 ‘입장 토큰’을 발급한다. 유저는 이 토큰을 X-Entry-Token 헤더에 담아 주문 API를 호출하게 된다. 이 단순해 보이는 구조, 과연 무엇이 문제였을까?

2. Queue에 넣었는데 DB가 터졌다: 마이크로 배칭
#

구현을 마치고 부하 테스트를 돌렸을 때 가장 먼저 마주한 문제는 **“줄을 세웠는데도 DB가 터진다”**는 것이었다. 여기서 나는 중요한 인식의 전환을 경험했다. 대기열이 있으니 순서대로 처리될 거라 생각했지만, 순서를 정하는 것과 한 번에 몇 명을 보낼지 제어하는 것은 별개의 문제였다.

“대기열은 순서를 정하는 장치이지, 유입 속도를 조절하는 장치가 아니다.”

2-1. ZPOPMIN을 한 번에 1000개 꺼낸다면?
#

만약 대기열에 10,000명이 있고, 스케줄러가 한 번에 1,000명씩 꺼내 토큰을 준다고 가정해 보자. 1,000명의 유저는 토큰을 받자마자 약속이라도 한 듯 동시에 주문 API를 호출할 것이다. 이는 대기열이 없을 때와 마찬가지로 Thundering Herd 현상을 발생시킨다. 대기열은 그저 폭발 시점을 조금 뒤로 미룬 방패에 불과했던 것이다.

2-2. 100ms마다 18명 — 배치 주기를 결정한 근거
#

시스템을 실제로 보호하려면 DB가 감당할 수 있는 **처리량(Throughput)**을 보수적으로 산정하고, 이를 아주 잘게 쪼개서 흘려보내야 한다. 나는 다음과 같은 산식을 통해 타겟 TPS를 도출했다.

  • DB 커넥션 풀: 50개
  • 평균 처리 시간: 200ms (재고 차감 + 쿠폰 검증 + 주문 저장 + 이벤트 발행)
  • 안전 마진: 70% (예상치 못한 스파이크 대비)
  • Target TPS: $(50 / 0.2) \times 0.7 = 175$ TPS

초당 175명을 한꺼번에 푸는 것(1s 배치)과 100ms마다 18명씩 푸는 것(마이크로 배칭)은 DB 입장에서 완전히 다른 부하 곡선을 그린다.

[1초 배치 부하 곡선]              [100ms 마이크로 배칭 부하 곡선]
TPS                              TPS
^                                ^
|   |                            |
|   |                            |  ----------------- (안정적 유량)
|   |                            |  | | | | | | | | |
|___|________________> Time      |__|_|_|_|_|_|_|_|_|_> Time
    (1초마다 피크 발생)                (부하가 고르게 분산됨)

배치 주기가 짧을수록 대기열의 흐름은 부드러워진다. 1초 배치는 유저에게 뚝뚝 끊기는 느낌을 주지만, 100ms 간격은 거의 실시간에 가까운 흐름을 만들면서도1 DB에 가해지는 순간 부하를 분산시킨다.

2-3. ZPOPMIN 직후 서버가 죽으면? (신뢰성의 함정)
#

여기서 또 하나의 고민이 생겼다. Redis의 ZPOPMIN은 요소를 원자적으로 제거하면서 반환한다. 스케줄러가 유저를 꺼낸 직후, 토큰을 발급하기 전에 서버가 크래시되면 해당 유저들은 대기열에서 사라졌지만 토큰은 받지 못한 ‘미아’ 상태가 된다.

이를 완벽히 해결하려면 3-Queue 모델(Pending → Processing → Completed) 도입이 필요하다. Lua Script를 이용해 Pending 큐에서 Processing 큐로 유저를 원자적으로 옮기고, 처리가 완료된 후에만 삭제하는 방식이다. 현재 내 프로젝트에서는 시스템 복잡도를 고려해 이를 미적용했다. 대신 마이크로 배칭 단위가 18명으로 작기 때문에, 크래시가 발생하더라도 최대 유실 규모가 18명으로 제한된다는 점에 기대고 있다. 유실된 유저는 재진입을 통해 대기열에 다시 합류할 수 있으므로, 완벽하지는 않지만 수용 가능한 트레이드오프라고 판단했다.

3. 서버를 늘렸더니 토큰이 3배 발급된다: 분산 락
#

시스템 가용성을 위해 서버를 3대로 늘리자마자 예상치 못한 문제가 터졌다. 초당 175명을 내보내기로 했는데, 실제로는 18명 × 10회 × 3대 = 540명이 나가고 있었던 것이다. 각 서버의 QueueScheduler가 독립적으로 작동하며 각자 18명씩 유저를 풀고 있었기 때문이다.

이를 해결하기 위해 Redis 분산 락을 도입했다.

// QueueScheduler.java 의 핵심 로직
@Scheduled(fixedDelay = 100)
public void publishTokens() {
    String lockKey = "lock:queue:scheduler";
    String lockValue = UUID.randomUUID().toString();
    // 500ms의 짧은 Lease Time으로 분산 락 획득 시도
    if (distributedLockRepository.acquire(lockKey, lockValue, 500)) {
        try {
            List<String> userIds = waitingQueueRepository.popMin(18);
            tokenService.issueTokens(userIds);
        } finally {
            distributedLockRepository.release(lockKey, lockValue);
        }
    }
}

분산 락은 효율성(Efficiency), 정확성(Correctness) 두 가지 목적으로 나눠볼 수 있다2. 대기열 스케줄러는 중복 실행을 막아 시스템 부하를 방지하는 ‘효율성’의 성격이 강하다. 설령 아주 드문 확률로 락이 튀어 토큰이 조금 더 발급되더라도, 최종 인터셉터에서 토큰 유효성을 검증하므로 데이터 정합성이 깨지지는 않는다. 따라서 Redlock 같은 무거운 도구 대신, 단일 Redis를 이용한 SET NX EX로도 충분하다는 판단을 내렸다.

다만 순간적으로 계획보다 많은 유저가 유입되어 DB 부하가 일시적으로 높아질 가능성은 남아 있다. 이를 위해 앞서 Target TPS를 산정할 때 30%의 안전 마진을 확보해 둔 것이기도 하다. 또한 해제 시에는 자신이 획득한 락만 삭제하도록 Lua Script로 소유권을 검증한다. 단순 DEL로 해제하면 lease 만료 후 다른 인스턴스의 락까지 지워버릴 수 있기 때문이다.

4. 토큰 받고 안 오는 유저가 슬롯을 먹는다: 토큰 생명주기
#

어렵게 발급한 토큰이 ‘유령 슬롯’이 되는 상황도 막아야 했다. 유저가 대기열을 뚫고 토큰을 받았는데 정작 주문 버튼을 누르지 않고 창을 닫아버리면, 그 유량만큼 다른 유저들의 입장이 늦어지기 때문이다.

이 문제는 RedisEntryTokenRepository와 EntryTokenInterceptor로 해결했다.

  1. 5분 만료 TTL: 토큰 발급 시 SET EX 300을 통해 5분 뒤면 자동으로 슬롯이 반환되게 했다.
  2. Lua Script를 이용한 원자적 소비: 주문 API(POST /api/v1/orders)에 도달했을 때, 인터셉터는 X-Entry-Token 헤더를 확인하고 토큰을 즉시 삭제한다. 이때 조회와 삭제 사이의 시간차(TOCTOU)를 없애기 위해 Lua Script를 사용했다.
-- validate-and-consume.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end

이 장치 덕분에 한 번 사용된 토큰은 재사용될 수 없으며, 사용되지 않은 토큰은 정해진 시간 뒤에 사라져 불필요한 리소스 점유를 방지한다.

5. 정리: 대기열은 파이프라인이다
#

대기열을 구현하며 얻은 가장 큰 교훈은, 대기열이 단순한 ‘저장소’가 아니라 정교하게 설계된 파이프라인이어야 한다는 점이었다.

깨지는 지점증상해결 장치
한 번에 전부 풀어줌DB Thundering Herd마이크로 배칭 (100ms / 18명)
서버 수만큼 스케줄러 실행토큰 과다 발급분산 락 (SET NX EX)
토큰 발급 후 미방문처리량 정체 (유령 슬롯)TTL + Lua 원자적 소비

Auto Scaling은 메트릭 수집부터 인스턴스 준비까지 최소 수 분이 걸리기 때문에 순간적인 트래픽 스파이크에는 늦다. 대기열은 그 공백을 메우는 역할을 한다.

줄을 세우는 것만으로는 부족하다. 그 줄이 어떻게 빠져나가고, 어떻게 소멸되는지까지 관리해야 비로소 시스템은 안전해진다.
