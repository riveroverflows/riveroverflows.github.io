TL;DR
  • 과제 요구사항은 “일간 메트릭 테이블을 읽어 주간/월간을 집계"하라고 명시했다. 그러나 기존 product_metrics는 상품당 1레코드 누적 구조였다.
  • 세 가지 방향을 비교했다: (A) 기존 스키마 변경, (B) 일별 테이블 신설, (C) Redis ZSET 직접 사용.
  • B를 선택했다. 쓰기 경로를 이중화하는 대가로 배치·API 경로가 단순해지고, 기존 누적 테이블의 의미를 보존할 수 있었다.
  • 선택이 끝이 아니었다. ln(a) + ln(b) ≠ ln(a+b) 문제로 주문 점수는 daily에 미리 누적해야 했고, ISO 주차 연도 경계 때문에 기간 컬럼은 분리해야 했다.

지난 라운드에서 실시간 일간 랭킹을 Redis Sorted Set으로 만들었다. 이번 라운드는 같은 랭킹을 주간·월간으로 확장한다. 과제는 이렇게 요구한다.

하루치 메트릭 테이블(product_metrics)을 읽어 Spring Batch로 집계 결과를 적재하라.

문구만 보면 간단한 과제다. JdbcPagingItemReader로 일간 테이블을 읽고, GROUP BY로 집계하고, MV 테이블에 쓰면 끝이다. 현실은 그렇지 않았다. 과제가 전제한 “일간 메트릭 테이블"이 실제로는 존재하지 않았기 때문이다.

1. 문제 정의: 일간 집계 소스의 부재
#

1.1 현재 product_metrics의 구조
#

Round 7에서 만든 product_metrics는 상품당 1레코드의 전체 누적 테이블이다.

항목구조
키product_id UNIQUE — 상품당 1행
날짜컬럼 없음
갱신Kafka 이벤트마다 같은 행의 카운터를 증가

조회수, 좋아요 수, 판매 수량이 “누적값"으로만 존재한다. 오늘의 값을 계산하려면 전일 스냅샷을 따로 저장해 뒀다가 빼야 한다. 과제 문구가 말하는 “하루치"는 이 스키마에서 물리적으로 파생 불가능한 개념이다.

1.2 Redis ZSET도 대안이 아니다
#

Round 9에서 만든 ZSET(ranking:all:yyyyMMdd)은 일자별로 분리되어 있다. 그쪽이 주간 소스로 적합할까? 답은 아니다.

  • TTL 2일: ZSET 키의 TTL을 2일로 잡았다. 주간(7일), 월간(30일) 집계에는 데이터가 남아있지 않다.
  • 구조 불일치: ZSET의 score는 이미 가중치가 적용된 합산 점수다. view/like/order가 분리되어 있지 않아 배치에서 재집계하려면 분해가 불가능하다.

TTL을 늘리자는 제안도 가능하지만 Redis 메모리는 비싸다. 상품 카탈로그 규모가 커질수록 30일치 일별 ZSET을 전부 메모리에 이고 있는 비용이 가파르게 오른다.

1.3 이 문제를 어떻게 부를까
#

이름을 붙여 두자. “과제 요구 스키마와 보유 스키마의 불일치”. 랭킹이라는 도메인 축으로 보면 Round 7의 product_metrics는 통계 대시보드용이었고, 이번 라운드가 요구하는 것은 시계열 집계용 소스다. 이름이 같았을 뿐 설계 목적이 다른 두 테이블이다.

이 불일치를 좁히는 방향은 크게 세 갈래다.

2. 세 가지 방향
#

2.1 A. 기존 product_metrics 스키마 변경
#

원리. product_metrics에 metric_date DATE 컬럼을 추가하고 복합 UNIQUE (product_id, metric_date)로 바꾼다. 기존 누적 개념은 “해당 일자 누적"으로 재정의한다.

장점. 테이블 개수가 늘지 않는다. 과제 문구와 가장 직접적으로 일치한다.

단점. 파급이 넓다. product_metrics를 참조하는 Round 7~9 코드가 전부 “이 테이블의 한 행은 상품 전체 누적이다"라는 전제로 작성되어 있다. JPQL, QueryDSL, QueryCache 키, 그리고 대시보드 쪽 조회 로직까지 뒤집어야 한다. 마이그레이션 중 과거 데이터의 “날짜 없음” 문제도 풀어야 한다(모든 과거 레코드를 어제자로 몰아둘지, 최초 생성일로 분산할지).

적합한 상황. 기존 product_metrics에 붙어 있는 코드가 적거나, 누적 통계라는 의미 자체를 버려도 되는 경우.

2.2 B. 일별 테이블 신설 (product_metrics_daily)
#

원리. 기존 누적 테이블은 손대지 않는다. 대신 일별 기록 전용 product_metrics_daily를 신설한다. commerce-streamer가 Kafka 이벤트를 소비할 때 누적 테이블과 일별 테이블 모두에 upsert한다.

┌──────────┐   PRODUCT_DETAIL_VIEWED   ┌──────────────────────┐
│  Kafka   │ ─────────────────────────▶│ commerce-streamer    │
└──────────┘                           │ KafkaMetricEventHandler│
                                       └────────┬─────────────┘
                                                ├──▶ product_metrics (누적)
                                                └──▶ product_metrics_daily (오늘)

장점.

  • 기존 product_metrics와 그 참조 코드를 건드리지 않는다. 회귀 위험이 0에 가깝다.
  • “누적 통계"와 “일별 기록"의 책임이 테이블 이름으로 분리된다.
  • JdbcPagingItemReader가 읽을 깔끔한 시계열 소스가 생긴다. 과제 문구가 기대하는 “하루치 테이블"과도 의미상 일치한다.

단점.

  • 쓰기 경로가 이중화된다. 이벤트 하나당 DB 왕복이 최소 2회 발생한다.
  • 두 테이블 사이의 정합성 문제가 새로 생긴다. 한쪽 upsert만 성공하고 다른 쪽이 실패하면 불일치가 남는다.

적합한 상황. 기존 코드의 회귀 위험을 최소화하고 싶고, 쓰기 경로에 부담이 2배가 되어도 인프라가 견딜 수 있는 경우.

2.3 C. Redis ZSET 직접 사용
#

원리. 일별 ZSET의 TTL을 30일 이상으로 늘리고 배치 소스로 쓴다.

장점. 새로운 테이블 없이 기존 인프라로 해결된다. 쓰기 경로에 변화가 없다.

단점.

  • 30일치 일별 ZSET을 전부 Redis 메모리에 유지해야 한다. 카탈로그 규모에 따라 비용이 급격히 오른다.
  • ZSET의 score는 이미 가중합이다. 시그널별(view/like/order) 분해가 불가능해 집계 로직을 조정할 수 없다.
  • 배치가 Redis를 스캔하는 구조는 ZRANGE의 전수 조회로는 가능하지만, 상품별 합산을 위한 GROUP BY 시맨틱이 Redis에서 자연스럽지 않다.

적합한 상황. 점수 구조가 고정되어 있고, 향후에도 시그널별 재가중이 필요 없는 경우. 그리고 메모리 비용을 감수할 수 있는 경우.

3. 나의 선택: B, 그리고 그 뒤에 따라온 결정들
#

3.1 왜 B였는가
#

A는 원칙적으로 가장 깨끗하지만 마이그레이션 비용이 실제 위험으로 환산됐다. Round 7~9의 QueryCache 키, 관리자 대시보드 조회, product_metrics 기반 통합 테스트까지 한 번에 바꿔야 하는데, 이 라운드의 목표는 “배치 주간/월간 랭킹"이지 “메트릭 인프라 재설계"가 아니다. 범위를 벗어난 공사는 Cold Start 때 Carry-Over를 선택한 것과 같은 논리로 뒤로 미뤘다.

C는 메모리 비용도 문제지만, 시그널별 재가중을 포기해야 한다는 점이 컸다. 이번엔 기존과 같은 공식을 쓰지만, 다음 스프린트에 PM이 “좋아요 가중치를 1.5배로 올려보자"고 하는 순간 ZSET은 재구성할 수 없다. 배치가 시그널별 집계를 들고 있어야 이런 조정이 코드 변경 수 줄로 끝난다.

B를 택한 실질적 근거는 단순하다. 쓰기 경로의 부담은 수치화 가능한 비용이지만, 회귀 위험은 수치화가 어려운 비용이다. 회귀 위험이 더 무섭다.

3.2 쓰기 경로 이중화와 정합성
#

KafkaMetricEventHandler는 이벤트 하나를 받아 두 테이블에 upsert한다.

// PRODUCT_DETAIL_VIEWED 처리
val metric = productMetricRepository
    .findByProductId(productId)
    ?: ProductMetric.register(productId)
productMetricRepository.save(metric.recordView())

val daily = productMetricDailyRepository
    .findByProductIdAndMetricDate(productId, today)
    ?: ProductMetricDaily.register(productId, today)
productMetricDailyRepository.save(daily.recordView())

두 save는 같은 트랜잭션 안에서 실행된다. 둘 중 하나만 성공하는 경우는 없다. 하지만 이 구조는 두 쓰기의 독립 실패는 막지만, 동시 처리에 의한 경쟁 조건은 막지 못한다.

같은 (productId, metric_date)에 대해 서로 다른 컨슈머 인스턴스가 동시에 find → modify → save를 돌리면, 뒤에 오는 save가 앞의 변경을 덮어 쓴다. 현재는 concurrency=1 단일 인스턴스라 물리적으로 발생하지 않지만 설계 문서의 “9. 추후 개선"에 기록해 뒀다. 실무 해법은 INSERT ... ON DUPLICATE KEY UPDATE column = column + N이다1. 원자적 증분으로 find/modify/save의 경쟁 창을 제거할 수 있다.

3.3 order_score를 daily에 미리 누적한다
#

기존 실시간 ZSET의 점수 공식은 이렇다.

$$ \text{score} = 0.1 \cdot \text{view} + 0.2 \cdot \text{like} + 0.7 \cdot \ln(\text{amount}) $$

view_count, like_count는 daily에 건수로 저장하고 배치에서 SUM×가중치로 재구성하면 된다. 그런데 주문 점수는 그렇게 되지 않는다.

$$ \ln(a) + \ln(b) \neq \ln(a + b) $$

daily에 sales_amount = a + b 만 저장해 두면 나중에 ln(a + b)는 계산할 수 있지만, 기존 ZSET이 누적한 ln(a) + ln(b)를 재현할 수 없다. 두 값은 수학적으로 다른 수다. 랭킹이 기존과 일치하지 않는다.

해법은 daily 테이블에 order_score 컬럼을 추가하고, streamer가 주문 이벤트를 처리할 때 건별로 0.7 × ln(금액)을 직접 누적해 두는 것이다.

fun recordOrder(quantity: Int, amount: Long): ProductMetricDaily {
    if (amount <= 0) return copy(
        unitsSold = unitsSold + quantity,
        salesAmount = salesAmount + amount,
    )
    return copy(
        unitsSold = unitsSold + quantity,
        salesAmount = salesAmount + amount,
        orderScore = orderScore + RankingScorePolicy.ORDER_WEIGHT * ln(amount.toDouble()),
    )
}

배치는 이 order_score를 SUM만 하면 된다. 수학적 정확성과 실시간 ZSET과의 일관성을 모두 얻는다.

3.4 기간 컬럼은 분리해 둔다
#

주간 MV의 기간 키를 어떻게 잡을지 고민이 있었다.

  • 후보 1: year_week VARCHAR(7) 예: "2026-W16"
  • 후보 2: year INT, week INT 분리

후보 1이 짧아 보이지만 문자열 비교는 위험하다. "2026-W2"와 "2026-W10"을 문자열로 정렬하면 W10이 먼저 온다. 0-padding을 강제하면 피할 수 있지만 가드 한 줄을 놓치면 조용히 잘못된 순서로 섞인다.

그리고 주차 계산에는 ISO 8601 주차를 쓴다2. 이 스펙은 LocalDate.of(2027, 1, 1)이 2026-W53에 속할 수 있다. 달력 연도와 ISO 주차 연도가 어긋나는 경계가 존재한다는 뜻이다. Java에선 이 값을 따로 뽑아야 한다.

val year = baseDate.get(IsoFields.WEEK_BASED_YEAR)
val week = baseDate.get(IsoFields.WEEK_OF_WEEK_BASED_YEAR)

baseDate.year를 그대로 쓰면 연말·연초에 주차가 한 단위 틀어진다. IsoFields.WEEK_BASED_YEAR는 ISO 주차에 대응되는 연도를 반환한다. 후보 2로 가면 두 컬럼에 각각 담으면 끝이다. 조회 쿼리도 단순해진다.

SELECT * FROM mv_product_rank_weekly
WHERE year = ? AND week = ?
ORDER BY rank ASC;

월간은 ISO 이슈가 없지만 일관성을 위해 year, month로 동일하게 분리했다.

3.5 Chunk 모델과 집계의 구조적 제약
#

이 글의 범위는 “소스 테이블을 어디서 만들까"까지지만, 한 가지만 미리 언급해 둔다. Spring Batch의 Chunk-Oriented Processing은 Reader → Processor → Writer가 아이템 1개를 받아 1개를 반환하는 구조다3. GROUP BY product_id로 묶은 뒤 전체 정렬해서 상위 100개만 남기는 작업을 Processor에서 수행할 수는 없다.

해법은 명백하다. SQL에서 집계와 정렬과 LIMIT을 모두 완결하고, Reader가 이미 집계된 행을 반환하면 된다. Processor는 받은 행에 rank 번호(1~100)를 부여하는 역할로 좁혀진다.

SELECT
    product_id,
    SUM(view_count)   AS view_count,
    SUM(like_count)   AS like_count,
    SUM(order_score)  AS order_score,
    (SUM(view_count) * 0.1
        + SUM(like_count) * 0.2
        + SUM(order_score)) AS total_score
FROM product_metrics_daily
WHERE metric_date BETWEEN ? AND ?
GROUP BY product_id
ORDER BY total_score DESC
LIMIT 100;

대상 테이블의 (metric_date, product_id) 복합 인덱스가 있으면 Range Scan + Group이 깔끔하게 붙는다. 배치가 Reader에서 이 쿼리를 돌리고, Processor는 rank만 매기고, Writer가 MV로 쓴다. 이 구조 덕에 “SQL 엔진이 잘하는 일은 SQL에, 애플리케이션이 잘하는 일은 애플리케이션에"라는 분업이 자연스러워진다.

#

Round 10의 배치 소스 설계 단계에서 내린 결정을 표로 정리한다.

어떤 결정도 최종 답은 아니다. 카탈로그가 수십만 규모로 커지면 daily 테이블의 일일 삽입량이 부담이 될 수 있고, 그때는 파티셔닝이나 INSERT ... SELECT 기반 일일 리프레시가 후보에 오른다. 다중 인스턴스 배포로 전환되는 시점에는 INSERT ... ON DUPLICATE KEY UPDATE로 원자적 증분을 도입해야 한다. 시그널 가중치가 자주 바뀌는 도메인이면 order_score까지 daily에 누적하는 대신 원시 금액 히스토리를 따로 두는 형태가 더 낫다.

이 라운드의 교훈은 단순하다. 과제 문구가 가정한 스키마가 현실과 다를 때, 그 간극을 어디서 메울지가 곧 아키텍처 결정이 된다. 스키마를 바꿀지, 새 테이블을 만들지, 다른 저장소로 우회할지의 선택은 기술적 선호가 아니라 회귀 위험과 쓰기 경로 비용 사이의 비교로 결론지어야 한다.
