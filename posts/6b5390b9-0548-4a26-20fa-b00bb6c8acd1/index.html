부제: 나는 왜 테스트에 집중하지 못했을까

들어가며.. - 일주일 회고
#

작년부터 AI와 함께 개인 프로젝트를 개발하고있다. 흔히 말하는 바이브 코딩에 가깝다. 바이브 코딩 초기에 시작된 이 프로젝트는 말하기 부끄럽지만 테스트 코드 하나 없이 개발하고 있었다.

어느 날 이 프로젝트에서 기능 하나를 수정했는데, 전혀 예상하지 못한 다른 기능이 깨진 적이 있었다. 당시에는 밀려있는 기능 개발이 더 급했기 때문에 대충 수습하고 넘겼었다. 그런데 또 그런 일이 발생해버렸다. 그래서 그 때 테스트 코드를 작성해야겠다고 생각했다. 그리고 언제부턴가 “바이브 코딩할 때 테스트 코드는 필수다” 라는 말을 여기 저기서 들었던 것 같다. 그 말에 대해 온전히 이해하진 못했지만 그냥 그렇구나 했었다. 어쨌든 나도 문제를 겪었던 그 이후로는 기능을 수정하거나 새로 추가하는 기능에는 테스트 코드를 작성했다.

그런데 문제는 테스트 코드도 전부 바이브코딩으로 작성했다. 테스트 방법과 테스트 코드에 대해 공부하지 않았다. AI에게 테스트 대상 메서드의 역할이 무엇인지와 예시 테스트 케이스를 몇개 던져주고, 엣지 케이스 찾아달라 요청하고, 테스트 코드를 작성시켰다. 내가 테스트에 대해 잘 모르다보니 AI가 작성한 테스트 코드가 제대로 작성된건지 검증할 수가 없었다. 일단 예시 테스트 케이스를 검증할 수 있는 테스트를 잘 작성한 것 같았고 기능도 잘 돌아가니까 반영했다.

AI가 작성한 Service 코드는 God Service가 되어 있었다. 특정 부분만 테스트 하고 싶은데 그럴 수가 없었다. 테스트하기 좋은 코드에 대해서 알고 싶었고, AI에게도 그런 방향성을 지시하고 싶은 마음이 생겼었다.

이번 주차 주제는 AI Agents와 TDD였다. 이전에 느꼈던 테스트에 대한 갈증을 해소하기에 정말 좋은 주제였다. 그런데 나는 테스트에도, TDD에 집중하지 못하고 AI가 구현 시 참조할 작업 지시 문서를 만드는 데 시간을 더 많이 썼다. 결과는.. 이도 저도 안됐다. 과제도 가장 늦게 제출했다. 아쉬웠다.

뒤늦게나마 발제에서 다룬 TDD, 검증 범위별 테스트, 테스트 도구에 대해 학습한 내용을 정리해보려고 한다.

테스트 피라미드
#

테스트 피라미드라는 개념을 이번에 처음 접했다. 그런데 신기하게도 그림을 보는 순간 “아, 이거구나” 싶었다. 이론적으로 완전히 이해한 건 아니지만, 내가 겪었던 경험들이 이 그림 안에서 설명되는 느낌이었다.

테스트는 범위에 따라 크게 세 가지 레벨로 나뉜다. 그리고 각 레벨은 역할과 책임이 다르다. 피라미드 하단일수록 빠르고 많이 작성하고, 상단일수록 느리지만 신중하게 구성한다.

단위 테스트 (Unit Test)
#

  • 대상: 도메인 모델 (Entity, VO, Domain Service)
  • 목적: 순수 로직의 정합성과 규칙 검증
  • 환경: Spring 없이 순수 JVM에서 실행

단위 테스트는 외부 의존성을 모두 제거하고 특정 로직만 격리해서 검증한다. 예를 들어 “포인트 충전 시 최대 한도를 초과하는지"만 확인하는 테스트다.

// 예시: 포인트 충전 로직 단위 테스트
@Test
fun `포인트 충전 시 최대 한도를 초과하면 예외 발생`() {
    val point = Point(amount = 900_000)

    assertThrows<IllegalArgumentException> {
        point.charge(200_000) // 최대 1,000,000 초과
    }
}

나는 지금까지 주로 단위 테스트를 작성했다. 단위 테스트는 작성하는 데 크게 부담이 없었다. 빠르게 실행되고, 실패하면 어디가 문제인지 바로 알 수 있었다.

통합 테스트 (Integration Test)
#

대상: 애플리케이션의 Service, Facade 등 계층 로직 목적: 여러 컴포넌트(Repo, Domain, 외부 API Stub)가 연결된 상태에서 비즈니스 흐름 전체를 검증 환경: @SpringBootTest, 실제 Bean 구성, Test DB

통합 테스트는 실제로 여러 컴포넌트가 함께 동작하는 걸 검증한다. 예를 들어 “포인트가 충전되고, DB에 반영되며, 이벤트가 발행되는 전 과정"을 확인한다.

@SpringBootTest
class PointServiceIntegrationTest {
    @Autowired
    lateinit var pointService: PointService

    @Test
    fun `포인트 충전 시 전체 흐름이 정상 동작한다`() {
        // given
        val userId = 1L
        val amount = 10_000

        // when
        val result = pointService.charge(userId, amount)

        // then
        assertThat(result.amount).isEqualTo(10_000)
        // DB 저장 확인, 이벤트 발행 확인 등
    }
}

통합 테스트는 솔직히 작성할 생각만 해도 마음에 벌써 부담이 느껴졌다. Spring을 띄워야 하고, DB도 필요하고, 설정도 복잡하고… 그래서 지금까지 한 번도 작성해본 적이 없다. 하지만 이번에 개념을 정리하면서, 통합 테스트가 왜 필요한지는 이해가 됐다. 컴포넌트들이 실제로 함께 동작할 때 발생하는 문제는 단위 테스트만으로는 잡아낼 수 없으니까.

E2E 테스트 (End-to-End Test)
#

대상: 전체 애플리케이션 (Controller → Service → DB) 목적: 실제 HTTP 요청 단위 시나리오 테스트 환경: MockMvc 또는 TestRestTemplate을 통해 실제 API 요청 시뮬레이션

E2E 테스트는 사용자 관점에서 전체 흐름을 검증한다. 예를 들어 “회원가입 → 포인트 충전 → 주문” 같은 실제 사용자 시나리오를 HTTP 요청으로 테스트한다.

@SpringBootTest
@AutoConfigureMockMvc
class UserE2ETest {
    @Autowired
    lateinit var mockMvc: MockMvc

    @Test
    fun `사용자 회원가입부터 주문까지 전체 흐름 테스트`() {
        // 1. 회원가입
        mockMvc.post("/api/users/register") { ... }

        // 2. 포인트 충전
        mockMvc.post("/api/points/charge") { ... }

        // 3. 주문
        mockMvc.post("/api/orders") { ... }
    }
}

E2E 테스트도 당연히 작성해본 적 없다. 통합 테스트보다 더 무겁고 복잡하니까.

테스트 피라미드를 보고 느낀 점
#

테스트 피라미드를 보면서, 내가 왜 단위 테스트만 작성했는지 이해가 됐다. 단위 테스트는 빠르고 가볍고 부담 없으니까. 그런데 문제는, 단위 테스트만으로는 내 코드가 실제로 제대로 동작하는지 보장할 수 없다는 거다.

특히 내가 겪었던 “Service 메서드 내부의 핵심 로직만 테스트하고 싶은데, 메서드 전체를 테스트해야 했던 문제"는 테스트 피라미드와도 연결된다. 내 코드는 단위 테스트하기 어려운 구조였던 거다. 여러 책임이 한 곳에 뭉쳐 있어서, 특정 부분만 격리해서 테스트할 수가 없었다.

이걸 개선하려면 테스트 가능한 구조로 변경해야 한다는 건 알겠는데, 아직 머릿속에 개념이 완전히 정립되진 않았다. 하지만 적어도 “왜 테스트하기 어려웠는지"는 이해하게 됐다.

테스트 더블 (Test Doubles)
#

테스트 더블이라는 용어는 이번에 처음 들었다. 그런데 알고 보니 내가 이미 사용하고 있던 것들이었다. mock(), given().willReturn(), verify() 같은 것들 말이다. 개인 프로젝트에서는 거의 안 썼지만, 업무에서는 자주 사용했다.

테스트 더블은 “테스트 대상이 의존하는 외부 객체의 동작을 빠르고 안전하게 흉내 내는 대역 객체"다. 느리고 불안정한 실제 구현(DB, 외부 API 등) 대신, 테스트 환경에 맞는 가짜를 사용한다.

역할과 도구의 구분
#

처음에 헷갈렸던 부분이 이거다. mock()이 Mock인 줄 알았는데, 그게 아니었다.

  • 역할: Stub, Mock, Spy, Fake (테스트 목적)
  • 도구: mock(), spy() (객체 생성 방식)

mock() 하나로 만든 객체에 Stub 역할과 Mock 역할을 동시에 부여할 수 있다.

Mock과 Stub의 차이
#

이 부분이 가장 헷갈렸다. “Mock이 가짜 객체를 세우는 거 아닌가?” 싶었는데, 정확히는:

  • Mock: “너 이 함수 호출했니?” (행위 검증)
  • Stub: “이렇게 호출하면, 이렇게 응답해줘” (상태 제공)

개인 프로젝트에서 작성했던(AI가..ㅎ) 테스트 코드를 다시 보니, 둘 다 사용하고 있었다.

@ExtendWith(MockitoExtension::class)
class AdminReviewProofServiceTest {

    @InjectMocks
    private lateinit var adminReviewProofService: AdminReviewProofService

    @Mock
    private lateinit var reviewProofRepository: ReviewProofRepository

    @Mock
    private lateinit var eventPublisher: ApplicationEventPublisher

    @Captor
    private lateinit var eventCaptor: ArgumentCaptor<ReviewProofNotificationEvent>

    @Test
    fun `리뷰 증빙 승인 시 상태 변경 및 이벤트 발행`() {
        // given - Stub 역할: 고정된 응답 제공
        val proof = pendingProof()
        val application = participatedApplication()

        given(reviewProofRepository.findById(anyLong()))
            .willReturn(Optional.of(proof))

        given(applicationRepository.findById(anyLong()))
            .willReturn(Optional.of(application))

        // when - 테스트 실행
        adminReviewProofService.updateReviewProof(proof.id, approvalDto)

        // then - Mock 역할: 호출 여부 검증
        verify(eventPublisher).publishEvent(eventCaptor.capture())

        val event = eventCaptor.value
        assertThat(event.userId).isEqualTo(application.userId)
        assertThat(event.eventType).isEqualTo(APPROVED)
    }
}

정리하면:

  • given().willReturn(): Stub 역할 - “이렇게 호출하면 이걸 줘”
  • verify(): Mock 역할 - “너 이거 호출했니?”

Stub만 사용하는 경우
#

@Test
fun `캠페인 조회 시 정보 반환`() {
    // given - Stub: 고정된 응답 제공
    val campaignRepository = mock<CampaignRepository>()
    given(campaignRepository.findById(100L))
        .willReturn(Campaign(
            id = 100L,
            name = "테스트 캠페인",
            status = ACTIVE
        ))

    // when
    val campaign = service.getCampaign(100L)

    // then - 반환값만 확인 (호출 여부는 관심 없음)
    assertThat(campaign.name).isEqualTo("테스트 캠페인")
    assertThat(campaign.status).isEqualTo(ACTIVE)
}

흐름만 통제하고 싶을 때 사용한다. “이렇게 호출하면, 이렇게 응답해줘”

Mock으로 사용하는 경우
#

@Test
fun `증빙 승인 시 알림 이벤트 발행`() {
    // given
    val eventPublisher = mock<EventPublisher>()
    val service = ProofService(eventPublisher = eventPublisher)

    // when
    service.approveProof(proofId = 1L, approvedBy = "admin")

    // then - 호출 여부 확인 (반환값은 관심 없음)
    verify(eventPublisher).publishEvent(any<ProofApprovedEvent>())
    verify(eventPublisher, times(1)).publishEvent(any())
}

호출 여부가 검증 대상일 때 사용한다. “너 이렇게 동작했니?”

둘 다 사용하는 경우 (가장 흔한 패턴)
#

@Test
fun `증빙 승인 시 상태 변경 및 알림 발행`() {
    // given - Stub: 의존성 응답 설정
    val proofRepository = mock<ProofRepository>()
    val applicationRepository = mock<ApplicationRepository>()
    val eventPublisher = mock<EventPublisher>()

    val proof = Proof(id = 1L, status = PENDING)
    val application = Application(id = 100L, userId = 50L)

    given(proofRepository.findById(1L))
        .willReturn(proof)
    given(applicationRepository.findById(100L))
        .willReturn(application)

    // when
    service.approveProof(proofId = 1L, approvedBy = "admin")

    // then - Mock: 호출 검증
    assertThat(proof.status).isEqualTo(APPROVED) // 상태 변경 확인
    verify(eventPublisher).publishEvent(argThat { event ->
        event.proofId == 1L && event.userId == 50L
    })
}

업무에서 작성했던 테스트가 대부분 이 패턴이었다. 의존성은 Stub으로 응답을 제어하고, 핵심 동작은 Mock으로 검증했다.

그 외: Spy와 Fake
#

Spy는 진짜 객체를 감싸서 일부만 조작한다.

@Test
fun `실제 로직 실행 후 호출 검증`() {
    val realService = RealService()
    val spyService = spy(realService)

    // when
    spyService.doSomething() // 진짜 로직 실행

    // then
    verify(spyService).doSomething() // 호출 검증
}

“로직은 그대로 쓰고, 특정 동작만 덮어씌우고 검증하고 싶다”

Fake는 실제처럼 동작하는 가짜 구현체다.

class InMemoryUserRepository : UserRepository {
    private val data = mutableMapOf<Long, User>()

    override fun save(user: User) {
        data[user.id] = user
    }

    override fun findById(id: Long) = data[id]
}

실제 DB 없이 테스트할 수 있다. “완전히 독립적인 테스트 환경이 필요할 때”

테스트 더블을 이해하고 나서
#

개념을 정리하고 나니, 내가 업무에서 작성했던 테스트들이 이해가 됐다. 그냥 “패턴대로” 따라 했던 게 아니라, 각 도구의 역할이 있었던 거다.

하지만 개인 프로젝트에서는 여전히 문제가 있다. God Service 메서드가 너무 많은 걸 하고 있어서, 테스트 더블을 써도 테스트하기 어렵다. 메서드 전체를 실행해야 하니까, 특정 부분만 검증하는 게 불가능하다.

이걸 해결하려면 “테스트 가능한 구조"로 변경해야 한다.

테스트 가능한 구조
#

“테스트 가능한 구조"란, 검증하고 싶은 로직을 외부 의존성과 격리된 상태에서 단독으로 검증할 수 있는 구조다. 쉽게 말하면, 조용하고 단단하게 확인할 수 있는 구조다.

개인 프로젝트의 Service 메서드를 다시 보니, 왜 테스트하기 어려웠는지 명확하게 보였다.

문제: 하나의 메서드가 너무 많은 일을 한다
#

개인 프로젝트의 한 Service 메서드는 약 65줄에 걸쳐 여러 책임을 모두 처리하고 있었다:

class ProofService(
    private val proofRepository: ProofRepository,
    private val applicationRepository: ApplicationRepository,
    private val contentService: ContentService,
    private val eventPublisher: EventPublisher
) {
    fun updateProof(proofId: Long, dto: UpdateDto) {
        // 1. 데이터 조회
        val proof = proofRepository.findById(proofId) ?: throw NotFoundException()
        val application = applicationRepository.findById(proof.applicationId) ?: throw NotFoundException()

        // 2. 피드백 업데이트
        dto.feedback?.let {
            proof.feedback = it
            proof.feedbackDate = LocalDateTime.now()
        }

        // 3. 승인 처리
        if (dto.status == APPROVED) {
            proof.approve()

            // 3-1. 예산 검사
            checkBudgetExceed(application.campaign, proof.paymentAmount)

            // 3-2. 상태 변경
            application.status = PARTICIPATED

            // 3-3. 콘텐츠 배정
            try {
                contentService.assignContent(application.id)
            } catch (e: Exception) {
                log.warn("콘텐츠 배정 실패", e)
            }

            // 3-4. 이벤트 발행
            eventPublisher.publish(ApprovedEvent(proof.id))
        }

        // 4. 데이터 동기화
        syncOrderInfo(proof, dto)
    }

    private fun checkBudgetExceed(campaign: Campaign, amount: BigDecimal) {
        if (campaign.totalSpent + amount > campaign.budget) {
            campaign.status = PAUSED
        }
    }
}

문제점:

  • “승인 시 예산 초과 검사” 로직만 테스트하고 싶은데 불가능
  • 메서드 전체를 실행해야만 함
  • Repository 2개 + ContentService + EventPublisher를 모두 Mock으로 설정해야 함

해결: 책임을 분리한다
#

핵심 원칙:

  1. 외부 의존성 분리 (인터페이스 + DI)
  2. 비즈니스 로직 분리 (도메인 엔티티로 위임)
  3. 책임 단일화 (한 함수는 한 역할만)

개선된 구조:

// 1. 예산 검사 로직을 별도 클래스로 분리
class BudgetValidator {
    fun checkAndPause(campaign: Campaign, amount: BigDecimal) {
        if (campaign.shouldPauseBy(amount)) {
            campaign.pause()
        }
    }
}

// 2. 도메인 로직은 Entity로 위임
class Campaign(
    val budget: BigDecimal,
    var totalSpent: BigDecimal = BigDecimal.ZERO,
    var status: CampaignStatus = ACTIVE
) {
    fun shouldPauseBy(amount: BigDecimal): Boolean {
        return totalSpent + amount > budget
    }

    fun pause() {
        status = PAUSED
    }
}

// 3. Service는 흐름만 조율
class ProofService(
    private val proofReader: ProofReader,
    private val budgetValidator: BudgetValidator,
    private val contentAssigner: ContentAssigner,
    private val eventPublisher: EventPublisher
) {
    fun approveProof(proofId: Long, dto: ApprovalDto) {
        val proof = proofReader.get(proofId)
        val application = proofReader.getApplication(proof.applicationId)

        // 도메인 로직 실행
        proof.approve(dto.approvedBy)
        application.participate()

        // 검증 및 부가 작업
        budgetValidator.checkAndPause(application.campaign, proof.paymentAmount)
        contentAssigner.tryAssign(application.id)
        eventPublisher.publish(ProofApprovedEvent(proof.id))
    }
}

이제 각 부분을 독립적으로 테스트 가능:

// 예산 검사 로직만 단위 테스트
@Test
fun `예산 초과 시 캠페인 중단`() {
    val campaign = Campaign(budget = 100_000.bd, totalSpent = 60_000.bd)

    val validator = BudgetValidator()
    validator.checkAndPause(campaign, 50_000.bd)

    assertThat(campaign.status).isEqualTo(PAUSED)
}

// 도메인 로직만 순수 테스트 (의존성 없음)
@Test
fun `총 지출이 예산 초과하면 true`() {
    val campaign = Campaign(budget = 100_000.bd, totalSpent = 80_000.bd)

    val result = campaign.shouldPauseBy(30_000.bd)

    assertThat(result).isTrue()
}

// Service는 흐름만 검증 (Mock 사용)
@Test
fun `승인 시 예산 검사 및 이벤트 발행`() {
    val budgetValidator = mock<BudgetValidator>()
    val eventPublisher = mock<EventPublisher>()

    service.approveProof(proofId = 1L, dto = approvalDto)

    verify(eventPublisher).publish(any<ProofApprovedEvent>())

변화의 핵심
#

BeforeAfter
하나의 메서드 = 모든 책임책임별로 메서드/클래스 분리
모든 의존성 Mock 필요필요한 부분만 Mock
특정 로직만 테스트 불가능각 부분을 독립적으로 테스트
도메인 로직이 Service에 흩어짐Entity에 위임 (순수 테스트 가능)

아직 감이 안 오는 부분
#

이론은 이해했는데, 실제로 적용하려면 여전히 어렵다. “이 메서드를 어떻게 쪼개야 할까?” “어디까지가 Service 책임이고, 어디부터가 도메인 책임일까?” 같은 질문들이 생긴다.

하지만 적어도 방향은 알게 됐다:

  1. 한 메서드가 너무 많은 일을 하면 → 책임별로 분리
  2. 특정 로직만 테스트하고 싶으면 → 그 로직을 별도 메서드/클래스로 추출
  3. 외부 의존성이 하드코딩되어 있으면 → 인터페이스로 추상화하고 주입받기

TDD (Test-Driven Development)
#

TDD는 “테스트 먼저 작성 → 코드 구현 → 리팩토링"의 사이클을 반복하는 개발 방법론이다. 발제에서는 이렇게 설명했다:

TDD는 테스트의 순서보다 “설계 단위를 잘게 쪼개고, 그것이 검증 가능하게 구현되었는가” 가 핵심이다.

Red → Green → Refactor
#

TDD의 3단계 루프:

1. Red: 실패하는 테스트 작성
2. Green: 통과할 최소한의 코드 작성
3. Refactor: 구조 개선 및 리팩토링
→ 반복

이론은 이해했다. 그런데 이번 주차에서 나는 TDD를 제대로 경험하지 못했다.

내가 TDD에 집중하지 못한 이유
#

과제 제출 기한이 얼마 안 남았을 때, 급하게 AI에게 “Red-Green-Refactor 사이클로 개발해줘"라고 요청하긴 했다. 하지만 이건 내가 경험했다고 할 수 없다. AI가 한 거지, 내가 한 게 아니니까.

더 근본적인 이유는 지시 문서 작성에 집중했다는 거다.

이전 회사에서 바이브 코딩을 통한 높은 생산성을 요구받았다. 바이브 코딩을 할 때마다 느낀 건, “AI에게 어떤 컨텍스트를 주고, 어떤 요청을 어떻게 하느냐"가 결과를 좌우한다는 거였다. 당시 AI 에이전트는 지금처럼 말을 잘 알아듣지 못했다. 그러다 보니 요구사항 문서를 잘 작성해야 한다는 게 머리에 박혔다.

회사를 그만둔 지 벌써 6개월이 지났는데도, AI와 개발하려면 문서를 잘 작성해야 한다는 생각이 먼저 든다. 그래서 이번 주차에서도 TDD보다 “AI가 참조할 작업 지시 문서"를 만드는 데 시간을 더 많이 썼다.

결과는 이도 저도 안 됐다. 과제도 가장 늦게 제출했다.

AI 시대에 TDD가 필요할까?
#

솔직히 이런 생각이 든다:

AI와 같이 개발하는데, 굳이 Red → Green → Refactor 사이클을 지켜야 할까?

인수 조건만 잘 작성해두면, AI가 인수 조건에 맞는 코드와 테스트를 한 번에 작성하면 되지 않을까? Red → Green → Refactor 순서대로 하면 토큰도 많이 소모되고, 시간도 오래 걸린다.

하지만 발제 내용을 다시 보면:

TDD가 필요한 이유:

  • 요구사항을 먼저 정리할 수 있다
  • 작게 쪼개고 점진적으로 설계하게 된다
  • 인터페이스 설계가 자연스럽게 나온다
  • 리팩토링이 가능해진다

AI가 코드를 작성하더라도, 이 “작게 쪼개고 점진적으로 설계"하는 과정은 여전히 필요하다. 오히려 AI가 만든 코드가 God Service가 되지 않으려면, 내가 먼저 “어떤 단위로 쪼갤지"를 설계해야 한다.

TFD vs TLD
#

발제에서 소개한 두 가지 접근:

전략설명적합한 상황
TFD (Test First Development)테스트 먼저 작성 → 코드를 맞춰 구현도메인/로직 중심
TLD (Test Last Development)코드를 먼저 작성 → 테스트는 나중에API/계층 설계가 먼저 필요한 상황

AI와 개발할 때는 TLD가 더 자연스러울 수도 있다. “이런 API가 필요해” → AI가 구현 → “이제 테스트 작성해줘”

하지만 핵심은 **순서가 아니라 “검증 가능하게 설계했는가”**다.

다음 과제
#

이번 주차를 돌아보면 아쉽다. TDD에 집중하지 못했고, 테스트 가능한 구조로 설계하지도 못했다. 그냥 급하게 “AI한테 TDD로 해줘” 하고 넘어갔다.

하지만 적어도 이해는 했다:

  • 테스트 피라미드: 단위/통합/E2E의 역할
  • 테스트 더블: Mock과 Stub의 차이
  • 테스트 가능한 구조: 책임 분리의 중요성
  • TDD: 순서보다 “검증 가능한 설계"가 핵심

다음부터는 AI에게 “이거 만들어줘"가 아니라, “이 책임은 이렇게 분리하고, 이 부분은 이렇게 테스트할 수 있게 해줘"라고 지시할 수 있을 것 같다.

AI 시대에도 테스트는 여전히 중요하다. 아니, 오히려 더 중요할지도 모른다. AI가 만든 코드가 정말 내가 의도한 대로 동작하는지 검증할 수 있는 건, 결국 테스트뿐이니까.

마치며
#

일주일이 지나고 나니, “왜 TDD에 집중하지 못했을까"라는 제목의 답이 명확해졌다.

테스트의 중요성은 알고 있었다. 그런데 “어떻게” 테스트해야 하는지, “무엇을” 테스트해야 하는지, “왜” TDD가 필요한지는 몰랐다. 그러다 보니 AI에게 의존하게 됐고, AI가 만든 코드가 테스트하기 어려운 구조인지조차 몰랐다.

이번 주차에는 과제도 늦게 냈고, TDD도 제대로 경험하지 못했다. 하지만 방향은 찾은 것 같으니 다음 주엔 더 열심히 “잘” 해봐야겠다.
