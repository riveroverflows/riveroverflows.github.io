TL;DR
  • 유연함은 공짜가 아니다.
  • EAV는 스키마 변경 없는 확장성을 주지만, 정합성과 쿼리 단순성을 희생할 가능성이 크다.
  • 일반적인 이커머스에서는 정규화된 컬럼 + JSON 하이브리드가 더 실용적이다.

작성 배경
#

이번 주 과제로 이커머스 상품 도메인을 설계하면서, 상품 속성을 어떻게 저장할지 다시 고민하게 됐다. 과거 프로젝트에서 사용했던 구조를 떠올려 AI에게 설명했더니 이런 답을 받았다.

그건 EAV(Entity-Attribute-Value) 패턴이고, RDBMS에서 자주 비판받는 방식입니다.

구현 당시에는 최선의 선택이라고 믿었는데, 왜 그렇게 불리는지 정확히 정리해 본 적은 없었다. 이번 글에서는 EAV가 왜 복잡도를 키웠는지, 그리고 이번 설계에서는 어떤 선택을 했는지 정리한다.

유연함의 대가, EAV
#

EAV 모델은 엔티티의 속성을 (entity, attribute, value) 형태로 저장해, 스키마 변경 없이 속성을 추가할 수 있게 만든 패턴이다.12 속성이 자주 바뀌고 엔티티별 속성이 크게 다른(희소한) 도메인에서는 유효하다.3 문제는 일반적인 상품 도메인에 그대로 적용하면 장점보다 비용이 커지기 쉽다는 점이다.

테이블만 보면 유연해 보이지만, 실제로는 속성 조합과 검증 책임이 애플리케이션으로 많이 이동한다.

데이터베이스 위의 데이터베이스: 내부 플랫폼 효과
#

EAV가 불편했던 이유를 따라가 보면 결국 내부 플랫폼 효과다.4 즉, RDBMS의 기능을 활용하지 않고 애플리케이션에서 비슷한 기능을 다시 구현하는 상태다.

  1. 타입 강제 어려움: value가 문자열이면 숫자/날짜/불리언 검증을 코드에서 처리해야 한다.5
  2. 제약 조건 관리 부담: 필수 값, 유니크, 도메인 규칙을 DB 레벨에서 일관되게 강제하기 어렵다.6
  3. 조회 복잡도 증가: 속성 조립을 위해 JOIN/재매핑/형변환 코드가 커진다.6
fun findByProductId(productId: Long): ProductVariantProcessingData {
    val variants = variantReader.findByProductId(productId)
    val variantAttributes = mergeAllAttributesFrom(variants)

    // 타입 정보 조회 + 문자열 value 형변환 + 응답 조립
    return ProductVariantProcessingData.from(variants, attributeTypes, attributeValues)
}

유연함은 얻었지만, 정합성 검증과 조회 조립을 매번 코드로 해결해야 했다.

학습을 위한 설계: 복잡도 덜어내기 (To-Be)
#

이번 과제에서는 확장성 욕심을 내려놓았다. EAV를 빼고 정규화된 모델로 단순화했다.

  • 공통 속성은 컬럼으로 명시적으로 관리
  • 재고는 성격이 다르므로 상품 마스터와 분리

실제 이커머스라면: Hybrid Approach
#

실무처럼 카테고리와 속성이 크게 늘어나는 상황에서는 다시 고민이 필요하다. 요즘은 정규화 모델에 JSON 컬럼을 혼합하는 하이브리드 접근이 널리 사용된다.78 이 글의 SQL 예시는 MySQL 8 기준이다.9 동일한 JSON 타입이라도 DBMS마다 구현과 제약이 다를 수 있으므로, 운영 DB 문서를 기준으로 검증하는 것이 안전하다.10

  • 검색/정렬 핵심 필드: 일반 컬럼 + 인덱스
  • 자주 바뀌는 상세 스펙: JSON 컬럼
erDiagram
    PRODUCT {
        bigint id PK
        varchar name "인덱싱/검색용"
        decimal price "인덱싱/정렬용"
        json attributes "가변 속성"
    }

로직의 변화
#

EAV에서 고통스러웠던 속성 재조립 로직이 크게 줄어든다. ORM에서 JSON을 객체/Map으로 매핑하면 단일 조회로 처리 가능한 범위가 넓어진다.

@Entity
@Table(name = "products")
class Product(
    @Id
    val id: Long,

    val name: String,

    val price: BigDecimal,

    @JdbcTypeCode(SqlTypes.JSON)
    @Column(columnDefinition = "json")
    val attributes: MutableMap<String, Any> = mutableMapOf()
)

fun getProduct(productId: Long): ProductDto {
    val product = productRepository.findById(productId).orElseThrow()
    return ProductDto.from(product)
}

속성 검색도 복잡한 다중 JOIN 대신 JSON 경로 조회로 단순화할 수 있다.

SELECT *
  FROM `products`
 WHERE `attributes` ->>'$.color' = 'Red';

결론
#

EAV 자체가 잘못된 건 아니다. 의료 데이터처럼 엔티티마다 속성이 완전히 다른 도메인에서는 여전히 쓸 만하다. 다만 이커머스 상품처럼 속성이 어느 정도 예측 가능한 도메인까지 EAV를 끌고 올 필요는 없었다.

돌이켜보면, “나중에 속성이 늘어나면?“이라는 걱정이 설계를 과하게 복잡하게 만들었다. 정작 필요했던 건 제약을 명확히 거는 것이었는데, 유연함에 매달리느라 그걸 놓쳤다.
