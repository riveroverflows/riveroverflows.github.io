TL;DR
  • JVM Lock(synchronized, ReentrantLock)은 단일 JVM 범위에서만 유효하다.
  • @Transactional 프록시 경계(락 해제 시점/커밋 시점, self-invocation)는 락 종류와 무관하게 반드시 같이 봐야 한다.
  • 재고, 쿠폰, 좋아요는 겉보기엔 비슷한 동시성 문제지만, 각각 다른 전략이 필요하다.
  • “어떤 락을 쓸까"보다 “이 문제의 성격이 뭔가"를 먼저 파악하는 게 핵심이다.

작성 배경
#

이커머스 과제에서 주문 기능을 구현하면서, 동시성 테스트를 작성해야 했다. 재고 차감, 쿠폰 이중 사용 방지, 좋아요 중복 방지 — 세 가지.

처음에는 솔직히 “전부 비슷한 거 아닌가?“라고 생각했다. 동시에 접근하면 깨지니까 락 걸면 되는 거 아닌가? 근데 직접 실험해보니까, 세 문제의 성격이 전부 달랐고, 그래서 해결 전략도 달라야 했다.

이 글은 그 과정을 정리한 것이다. synchronized 실험부터 비관적/낙관적/Named Lock 비교까지는 playground 실험 코드(concurrency, cbd771b, 1ebe919, 732dcc5, b72d428)를 기준으로 작성했다.

synchronized를 걸었는데 왜 깨지지?
#

가장 먼저 시도한 건 Java 개발자라면 자연스럽게 떠올릴 synchronized였다.

재고 차감 메서드에 synchronized를 걸고, 동시 요청 테스트를 돌렸다. 단일 JVM + 트랜잭션 없는 환경에서는 정상 동작했다.

문제는 트랜잭션 경계와 결합될 때였다. 실무 코드는 보통 @Transactional 위에서 돌아가고, 여기서 락 해제 시점과 커밋 시점이 어긋나는 구간이 생긴다.

원인: @Transactional의 프록시 경계
#

@Transactional은 Spring AOP 프록시로 동작한다. 개념적으로 호출 순서는 다음과 같다:

---
config:
  theme: dark
  handDrawn: true
---
sequenceDiagram
    participant T1 as Thread 1
    participant P as Proxy
    participant S as StockService
    participant T2 as Thread 2

    T1->>P: decrease() 호출
    P->>P: beginTransaction()
    P->>S: synchronized { decrease() }
    S-->>P: 메서드 종료 (synchronized 해제)
    Note over T2,P: 이 틈에 Thread 2 진입 가능
    T2->>P: decrease() 호출
    T2->>P: beginTransaction()
    T2->>S: synchronized { decrease() }
    P->>P: commit() ← Thread 1

synchronized 블록이 끝나는 시점과 트랜잭션이 커밋되는 시점 사이에 갭이 있다. 메서드 실행이 끝나면 JVM 락은 풀리지만, DB 반영은 아직 커밋 전일 수 있다.

추가로, 프록시를 설명할 때 꼭 같이 봐야 할 포인트가 있다.

  • @Transactional은 프록시를 거친 외부 호출에서만 적용된다.
  • 같은 클래스 내부 호출(self-invocation)은 프록시를 우회하므로, 내부 메서드의 @Transactional(REQUIRES_NEW 포함) 속성이 새로 적용되지 않는다.
  • 호출자에 트랜잭션이 없으면 내부 메서드는 트랜잭션 없이 실행되고, 호출자가 트랜잭션 안이면 그 트랜잭션에 그대로 참여한다.
  • 이 흐름은 playground 실험 코드에서도 동일하게 확인했다.

그럼 ReentrantLock은?
#

synchronized의 한계가 “암시적이라 타이밍 제어가 안 된다"는 거라면, ReentrantLock으로 명시적으로 제어하면 되지 않을까?

결론부터 말하면 같은 문제다. ReentrantLock이든 synchronized든 JVM이 제공하는 도구는 같은 JVM 프로세스 안에서만 유효하다. 서버가 2대 이상이면 각 JVM의 락은 서로를 모른다.

Virtual Thread + synchronized (요약)
#

JDK 21~23에서는 synchronized 구간에서 pinning 이슈가 있어 Virtual Thread 효율이 떨어질 수 있었다. JDK 24(JEP 491)에서 이 부분이 완화되었다.

다만 이 글의 핵심 의사결정(재고/쿠폰/좋아요 전략 선택)은 DB 동시성 제어 기준이 중심이라, 상세 메커니즘은 부록으로 뺐다.

결론: JVM Lock에서 DB Lock으로
#

정리하면 JVM Lock에는 세 가지 한계가 있었다:

  1. 다중 서버에서 무력화 — 각 JVM의 락은 독립적
  2. 트랜잭션 프록시 경계 이슈 — 락 해제와 커밋이 같은 생명주기로 묶이지 않음
  3. Virtual Thread pinning 이슈 — JDK 24에서 완화

DB 레벨 락은 트랜잭션과 같은 생명주기로 동작한다.

DB 레벨 락으로 전환
#

SELECT ... FOR UPDATE는 row를 잠그고, 트랜잭션이 커밋/롤백될 때 함께 풀린다. JVM Lock처럼 “락 해제 → 커밋” 갭이 분리되지 않는다.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query(
    """
    SELECT ps
      FROM ProductStockEntity ps
     WHERE ps.productId IN :productIds
       AND ps.deletedAt IS NULL
     ORDER BY ps.productId ASC
    """,
)
fun findAllByProductIdInWithLock(productIds: List<Long>): List<ProductStockEntity>

실제 주문 구현에서는 productIds를 정렬해서(sorted) 락을 획득한다. 복수 상품 주문에서 락 순서를 고정해 데드락 가능성을 낮추기 위한 선택이다.

잠깐, 모든 문제에 비관적 락?
#

재고 문제는 해결했다. 그런데 쿠폰 이중 사용 방지도 비관적 락? 좋아요 중복 방지도?

여기서 멈춰서 생각해봤다. 세 문제를 나란히 놓으면 성격이 다르다.

문제핵심 질문동시 요청 시 기대 결과
재고 차감10명이 동시에 1개씩 주문하면?재고 있는 한 전부 성공
쿠폰 이중 사용같은 쿠폰으로 2곳에서 동시 주문하면?1명만 성공, 나머지 실패
좋아요 중복같은 사람이 빠르게 2번 탭하면?1건만 등록, 에러 없음

“전부 성공시켜야 하는 문제"와 “1명만 성공하면 되는 문제"는 근본적으로 다르다.

재고 차감: 대기해서라도 전부 성공시켜야 한다
#

재고가 10개 있고 10명이 주문하면, 10명 전부 성공해야 한다. 1명만 성공하고 9명이 재시도하는 건 말이 안 된다.

비관적 락(SELECT FOR UPDATE):

---
config:
  theme: dark
  handDrawn: true
---
sequenceDiagram
    participant A as Transaction A
    participant DB as Database (stock=10)
    participant B as Transaction B

    A->>DB: SELECT ... FOR UPDATE → stock=10, 행 잠금
    B->>DB: SELECT ... FOR UPDATE
    Note over B,DB: 대기 중... (A가 잠금 보유)
    A->>DB: UPDATE stock = 9
    A->>DB: COMMIT → 잠금 해제
    B->>DB: → stock=9, 잠금 획득
    B->>DB: UPDATE stock = 8
    B->>DB: COMMIT → 잠금 해제
    Note over DB: 결과: stock = 8 (정확)
  • 선행 트랜잭션이 끝날 때까지 대기
  • 갱신된 재고를 읽고 차감
  • 재시도 불필요

낙관적 제어 + 재시도라면?
#

playground에서 낙관락 재시도 루프를 직접 돌려봤다:

public void decrease(Long id, Long quantity) throws InterruptedException {
    while (true) {
        try {
            optimisticLockStockService.decrease(id, quantity);
            break;
        } catch (Exception e) {
            Thread.sleep(50);
        }
    }
}

재고가 충분해도 version 충돌이 나면 재시도 루프를 반복하게 된다. 결국 성공하더라도 스레드 수가 늘수록 충돌/대기 비용이 커진다.

비관적 락은 대기 후 순차 처리라 재시도가 없다. 그래서 “전부 성공시켜야 하는” 재고 차감에는 비관적 락이 더 맞았다.

참고로 Named Lock(GET_LOCK)도 실험했다. row lock과 다르게 문자열 키를 기준으로 DB 뮤텍스를 잡는 방식이다.

@Query(value = "SELECT get_lock(:key, 3000)", nativeQuery = true)
void getLock(String key);

@Query(value = "SELECT release_lock(:key)", nativeQuery = true)
void releaseLock(String key);

비관적 락의 한계
#

다만 이건 “일반적인 이커머스 주문” 시나리오에서의 판단이다. 1만, 10만 명이 동시에 몰리는 선착순 이벤트라면 하나의 row lock 대기열이 길어지고, 커넥션 풀이 고갈되면서 장애 전파가 생길 수 있다.

트래픽 수준이 달라지면 전략도 달라져야 한다. Redis 분산 락, 큐 기반 비동기 처리 등이 대안이 될 수 있다.

쿠폰 이중 사용: 1명만 성공하면 된다
#

같은 쿠폰으로 여러 기기에서 동시에 주문하는 건 비정상 케이스다. 이 경우 1명만 성공하면 충분하고, 나머지는 실패 처리하면 된다.

여기서 핵심은 실패 이유를 구분해서 알려줘야 한다는 점이다. “이미 사용된 쿠폰”, “만료된 쿠폰”, “소유자 불일치"는 사용자 메시지가 다르다.

낙관적 제어(version 조건부 UPDATE):

---
config:
  theme: dark
  handDrawn: true
---
sequenceDiagram
    participant A as Transaction A
    participant DB as Database
    participant B as Transaction B

    A->>DB: SELECT coupon (AVAILABLE, version=0)
    B->>DB: SELECT coupon (AVAILABLE, version=0)
    A->>DB: UPDATE ... WHERE id=? AND version=0 AND status='AVAILABLE'
    Note over A,DB: 성공! version 0 -> 1
    B->>DB: UPDATE ... WHERE id=? AND version=0 AND status='AVAILABLE'
    Note over B,DB: 실패(영향 행 0건)

현재 구현은 @Version 예외에 의존하는 방식이 아니라, version 조건부 UPDATE 결과(row count)로 충돌을 판단한다:

@Modifying
@Query(
    """
    UPDATE IssuedCouponEntity e
       SET e.status = 'USED',
           e.usedAt = :usedAt,
           e.version = e.version + 1,
           e.updatedAt = :now
     WHERE e.id = :id
       AND e.version = :version
       AND e.status = 'AVAILABLE'
       AND e.deletedAt IS NULL
    """,
)
fun useOptimistic(...): Int
  • SELECT로 먼저 읽어서 도메인 상태를 검사한다(소유자/만료/사용 상태).
  • UPDATE 영향 행이 0이면 동시성 충돌로 본다(ISSUED_COUPON_CONFLICT).
  • 비정상 경쟁 상황에서는 1명만 성공하면 충분하므로, 대기시키는 비관적 락보다 이 모델이 단순했다.

좋아요 중복: 락이 필요 없다
#

좋아요는 (userId, productId) 조합이 유일해야 한다. 같은 사용자가 빠르게 두 번 탭하면?

DB에 UNIQUE(user_id, product_id) 제약이 걸려있다. 중복 INSERT를 시도하면 DB가 거부한다. 그리고 애플리케이션에서 해당 예외를 멱등 성공으로 처리하면 된다.

try {
    productLikeJpaRepository.saveAndFlush(productLikeMapper.toEntity(productLike))
} catch (e: DataIntegrityViolationException) {
    // 멱등 처리: 이미 존재하므로 정상 반환
}

여기에 비관적/낙관적 락을 추가하는 건 과잉이다.

정리: 문제의 성격이 전략을 결정한다
#

문제성격전략핵심 판단
재고 차감가능한 한 전부 성공비관적 락대기 후 순차 처리, 재시도 불필요
쿠폰 이중 사용1명만 성공 + 실패 이유 필요version 조건부 UPDATE 기반 낙관적 제어선읽기로 상태 구분 + 충돌 시 실패 처리
좋아요 중복중복만 막으면 됨UNIQUE 제약락 자체가 불필요

“동시성 문제 = 비관적 락"이라는 공식은 없었다. 각 문제를 분리해서 보면:

  1. 동시 요청 시 기대 결과가 뭔가? (전부 성공 vs 1명만 성공 vs 중복 방지)
  2. 실패 시 사용자에게 뭘 알려줘야 하나? (실패 이유 구분 필요 여부)
  3. 재시도가 필요한가? (비관적은 대기, 낙관적은 실패+재시도/충돌 처리)

이 세 질문에 답하면 전략이 자연스럽게 정해졌다.

배운 점
#

JVM Lock과 DB Lock은 같은 목적, 다른 레이어다. 읽기와 쓰기 사이에 다른 요청이 끼어드는 것을 막는다는 점은 같다. 하지만 어떤 레이어(JVM/DB)에서 어떤 생명주기(메서드/트랜잭션)로 제어하느냐에 따라 결과가 달라진다.

트래픽 수준이 바뀌면 전략도 바뀌어야 한다. 10명이 주문하는 일반 주문과 10만 명이 몰리는 선착순 이벤트는 같은 “재고 차감"이어도 다른 문제다.

“어떤 락을 쓸까"보다 “이 문제의 성격이 뭔가"가 먼저다. 락은 도구고, 전략은 기대 결과와 실패 모델에서 나온다.

부록: Virtual Thread와 synchronized 메모
#

JDK 21~23에서는 synchronized 블록에서 pinning 이슈가 있어 Virtual Thread가 carrier thread를 오래 점유할 수 있었다. 이 때문에 특정 워크로드에서 처리량 저하가 관찰될 수 있었다.

JDK 24의 JEP 491에서 이 동작이 완화되었고, 현재는 synchronized 사용 자체를 무조건 피해야 하는 상황은 아니다. 다만 동시성 제어를 JVM 내부 락으로 끝낼지, DB 트랜잭션 경계로 가져갈지는 별개의 설계 문제다.
