TL;DR
  • JVM Lock(synchronized, ReentrantLock)은 @Transactional과 함께 쓰면 동시성을 보장하지 못한다. 단일 서버에서도.
  • 재고, 쿠폰, 좋아요는 겉보기엔 비슷한 동시성 문제지만, 각각 다른 전략이 필요하다.
  • “어떤 락을 쓸까"보다 “이 문제의 성격이 뭔가"를 먼저 파악하는 게 핵심이다.

작성 배경
#

이커머스 과제에서 주문 기능을 구현하면서, 동시성 테스트를 작성해야 했다. 재고 차감, 쿠폰 이중 사용 방지, 좋아요 중복 방지 — 세 가지.

처음에는 솔직히 “전부 비슷한 거 아닌가?“라고 생각했다. 동시에 접근하면 깨지니까 락 걸면 되는 거 아닌가? 근데 직접 실험해보니까, 세 문제의 성격이 전부 달랐고, 그래서 해결 전략도 달라야 했다.

이 글은 그 과정을 정리한 것이다. synchronized가 왜 안 되는지 직접 확인한 것부터 시작해서, 세 가지 문제에 각각 다른 전략을 선택한 판단 근거까지.

synchronized를 걸었는데 왜 깨지지?
#

가장 먼저 시도한 건 Java 개발자라면 자연스럽게 떠올릴 synchronized였다.

재고 차감 메서드에 synchronized를 걸고, 10개 스레드로 동시에 1개씩 주문하는 테스트를 돌렸다. 재고 10개니까 최종 재고는 0이어야 한다.

결과: 재고가 0이 아니었다. 7이 나오기도 하고, 3이 나오기도 했다.

원인: @Transactional의 프록시
#

@Transactional은 Spring AOP 프록시로 동작한다. 실제 호출 순서가 이렇게 된다:

---
config:
theme: dark
handDrawn: true
---
sequenceDiagram
participant T1 as Thread 1
participant P as Proxy
participant S as StockService
participant T2 as Thread 2

T1->>P: decrease() 호출
P->>P: beginTransaction()
P->>S: synchronized { decrease() }
S-->>P: 메서드 종료 (synchronized 해제)
Note over T2,P: 이 틈에 Thread 2 진입 가능!
T2->>P: decrease() 호출
T2->>P: beginTransaction()
T2->>S: synchronized { decrease() }
Note over T2,S: 커밋 전 데이터를 읽는다
P->>P: commit() ← Thread 1

synchronized 블록이 끝나는 시점과 트랜잭션이 커밋되는 시점 사이에 갭이 있다. 메서드 실행이 끝나면 synchronized 락은 풀리지만, 프록시가 커밋하기 전이다. 이 틈에 다른 스레드가 들어오면 커밋 전 데이터를 읽는다.

직접 확인하고 싶어서 프록시 동작을 시뮬레이션하는 코드를 만들었다:

// 프록시가 하는 일을 직접 구현
fun decrease(id: Long) {
    startTransaction()           // 1. TX 시작
    stockService.decrease(id)    // 2. synchronized 메서드 호출 (여기서 락 획득/해제)
    endTransaction()             // 3. 커밋 ← synchronized 해제 이후!
}

@Transactional을 제거하고 synchronized만 남기면? 정상 동작했다. 하지만 이건 트랜잭션 보장이 안 되니까 실제로 쓸 수는 없다.

그럼 ReentrantLock은?
#

synchronized의 한계가 “암시적이라 타이밍 제어가 안 된다"는 거라면, ReentrantLock으로 명시적으로 제어하면 되지 않을까?

결론부터 말하면 같은 문제다. ReentrantLock이든 synchronized든 AtomicInteger든, JVM이 제공하는 동시성 도구는 전부 같은 JVM 프로세스 안에서만 유효하다. 서버가 2대 이상이면 각 JVM의 락은 독립적으로 동작하기 때문에 서로의 락을 모른다.

그리고 단일 서버라도 @Transactional 프록시와 조합하면 동일한 타이밍 갭이 발생한다. 락 해제 → 커밋 사이의 갭은 JVM Lock의 종류와 무관하게 Spring AOP 프록시 구조에서 오는 문제다.

Virtual Thread와 synchronized: Pinning 문제
#

JVM Lock의 한계는 또 있다. JDK 21에서 도입된 Virtual Thread와 synchronized를 함께 쓰면 **pinning(고정)**이 발생한다.

Virtual Thread는 원래 가벼운 스레드다. OS 스레드(carrier thread)에 올라타서 실행되다가, I/O 등 블로킹 작업을 만나면 carrier에서 내려와서(unmount) 다른 Virtual Thread가 그 carrier를 쓸 수 있게 한다. carrier thread는 기본적으로 CPU 코어 수만큼만 존재하므로, 이 mount/unmount가 핵심이다.

그런데 synchronized 블록 안에서는 이 unmount가 불가능했다. JVM이 모니터(monitor) 소유권을 platform thread 기준으로 추적했기 때문이다. Virtual Thread가 모니터를 잡은 채 unmount하면, 같은 carrier에 올라탄 다른 Virtual Thread가 그 모니터를 소유한 것처럼 보여서 상호 배제가 깨진다. 그래서 JVM이 synchronized 안에서는 unmount를 아예 막았다.

결과: synchronized 블록에서 블로킹이 발생하면 carrier thread가 통째로 묶인다. carrier가 CPU 코어 수(예: 8개)밖에 없는데 8개 모두 pinning되면? 나머지 Virtual Thread는 전부 대기하게 되고, Virtual Thread의 장점이 완전히 사라진다.

JDK 24에서 해결되었다. JEP 491로 모니터 소유권 추적 방식이 근본적으로 변경됐다. 기존에는 모니터의 소유자를 platform thread 포인터(JavaThread*)로 기록했지만, 이제는 **virtual thread의 ID(java.lang.Thread.tid)**로 기록한다. 모니터 소유권이 carrier와 독립적으로 유지되므로, synchronized 블록 안에서도 virtual thread가 자유롭게 unmount할 수 있게 됐고, Object.wait() 호출 시에도 마찬가지다.

남은 pinning 케이스는 클래스 로딩, 클래스 초기화, 네이티브 프레임이 스택에 있는 경우 정도인데, 실무에서 문제가 될 일은 거의 없다.

JEP 491 이전에는 synchronized 대신 ReentrantLock으로 교체하는 게 권장이었고, 많은 라이브러리가 실제로 이 작업을 했다. 하지만 JDK 24 이후 공식 권장은: “synchronized가 편리하고 에러가 적으니 실용적인 곳에서는 synchronized를 쓰고, 더 유연한 제어가 필요할 때만 ReentrantLock을 쓰라.”

결론: JVM Lock에서 DB Lock으로
#

정리하면 JVM Lock에는 세 가지 한계가 있었다:

  1. 다중 서버에서 무력화 — 각 JVM의 락은 독립적
  2. @Transactional 프록시와 타이밍 갭 — 락 해제 → 커밋 사이에 다른 스레드 진입
  3. Virtual Thread pinning — synchronized가 carrier thread를 묶어서 스케일링 불가 (JDK 24에서 해결)

DB 레벨에서 락을 걸어야 트랜잭션과 같은 생명주기로 동작한다.

DB 레벨 락으로 전환
#

SELECT FOR UPDATE는 해당 row를 잠그고, 트랜잭션이 커밋/롤백될 때 함께 풀린다. JVM Lock처럼 “락 해제 → 커밋” 사이의 갭이 없다.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT ps FROM ProductStockEntity ps WHERE ps.productId = :productId AND ps.deletedAt IS NULL")
fun findByProductIdWithLock(productId: Long): ProductStockEntity?

같은 테스트를 다시 돌렸다. UPDATE 쿼리 로그를 보면 10~20ms 간격으로 순차 실행되는 게 보인다:

35.108s - UPDATE product_stock SET quantity=9 ...
35.118s - UPDATE product_stock SET quantity=8 ...
35.137s - UPDATE product_stock SET quantity=7 ...
...

SELECT FOR UPDATE에서 대기하다가, 선행 트랜잭션이 커밋하면 갱신된 값을 읽고 차감한다. 재고가 남아있는 한 모든 요청이 순차적으로 성공한다. 재시도 로직이 필요 없다.

테스트 통과. 재고 10개, 10스레드, 최종 재고 0.

잠깐, 모든 문제에 비관적 락?
#

재고 문제는 해결했다. 그런데 쿠폰 이중 사용 방지도 비관적 락? 좋아요 중복 방지도?

여기서 멈춰서 생각해봤다. 세 문제를 나란히 놓으면 성격이 다르다.

문제핵심 질문동시 요청 시 기대 결과
재고 차감10명이 동시에 1개씩 주문하면?재고 있는 한 전부 성공
쿠폰 이중 사용같은 쿠폰으로 2곳에서 동시 주문하면?1명만 성공, 나머지 실패
좋아요 중복같은 사람이 빠르게 2번 탭하면?1건만 등록, 에러 없음

“전부 성공시켜야 하는 문제"와 “1명만 성공하면 되는 문제"는 근본적으로 다르다.

재고 차감: 대기해서라도 전부 성공시켜야 한다
#

재고가 10개 있고 10명이 주문하면, 10명 전부 성공해야 한다. 1명만 성공하고 9명이 재시도하는 건 말이 안 된다.

비관적 락(SELECT FOR UPDATE):

---
config:
theme: dark
handDrawn: true
---
sequenceDiagram
participant A as Transaction A
participant DB as Database (stock=10)
participant B as Transaction B

A->>DB: SELECT ... FOR UPDATE → stock=10, 행 잠금
B->>DB: SELECT ... FOR UPDATE
Note over B,DB: 대기 중... (A가 잠금 보유)
A->>DB: UPDATE stock = 9
A->>DB: COMMIT → 잠금 해제
B->>DB: → stock=9, 잠금 획득
B->>DB: UPDATE stock = 8
B->>DB: COMMIT → 잠금 해제
Note over DB: 결과: stock = 8 (정확!)
  • 선행 트랜잭션이 끝날 때까지 대기
  • 갱신된 재고를 읽고 차감
  • 재시도 불필요

낙관적 락이라면?
#

직접 실험해봤다. @Version 필드를 추가하고, version 충돌 시 재시도하는 Facade를 만들었다:

public void decrease(Long id, Long quantity) throws InterruptedException {
    while (true) {
        try {
            optimisticLockStockService.decrease(id, quantity);
            break;
        } catch (Exception e) {
            Thread.sleep(50);  // 재시도 전 대기
        }
    }
}

재고 100개, 스레드 100개로 돌렸을 때 로그를 보면 패턴이 보인다:

thread-25: SELECT ... version=3
thread-18: SELECT ... version=3         ← 같은 version을 읽음
thread-25: UPDATE ... WHERE version=3   ← 성공, version → 4
thread-18: UPDATE ... WHERE version=3   ← 실패! version 이미 4
  (50ms sleep)
thread-18: SELECT ... version=4         ← 재시도
thread-25: SELECT ... version=4         ← 또 같은 version
thread-18: UPDATE ... WHERE version=4   ← 성공
thread-25: UPDATE ... WHERE version=4   ← 또 실패!
  ...

while(true) 재시도 루프가 있어서 결국 전부 성공하긴 한다. 하지만 재고가 충분한데도 충돌-재시도가 끊임없이 반복된다. 스레드가 많아질수록 충돌 확률은 올라가고, 50ms sleep이 쌓여서 전체 처리 시간이 불필요하게 길어진다.

비관적 락은 대기 후 순차 처리라 재시도가 없다. 낙관적 락의 “실패 후 재시도” 모델은 “전부 성공시켜야 하는” 재고 차감에는 맞지 않았다.

그래서 재고 차감에는 비관적 락을 선택했다. 복수 상품 주문 시에는 productId ASC 순서로 락을 획득해서 데드락을 방지한다. 참고로 row 레벨 락 외에 MySQL의 Named Lock(GET_LOCK)도 실험해봤다. Named Lock은 DB가 관리하는 뮤텍스(한 번에 하나만 통과시키는 잠금장치)인데, 특정 row가 아니라 이름(문자열)을 키로 잡아서 락을 관리한다는 차이가 있었다. 순차 처리 결과는 동일했다.

비관적 락의 한계
#

다만 이건 “일반적인 이커머스 주문” 시나리오에서의 판단이다. 만약 1만, 10만 명이 동시에 선착순으로 몰린다면? 모든 트랜잭션이 하나의 row lock에 줄을 서게 되고, 커넥션 풀이 고갈되면서 다른 서비스까지 장애가 전파될 수 있다. 멘토링에서도 “선착순 시나리오에서 비관적 락은 단일실패지점(SPOF)“이라는 피드백을 받았다.

트래픽 수준이 달라지면 전략도 달라져야 한다. Redis 분산 락, 메시지 큐 기반 처리 등이 대안이 되지만, 이번 과제에서는 비관적/낙관적 락 학습에 집중하기로 했다.

쿠폰 이중 사용: 1명만 성공하면 된다
#

같은 쿠폰으로 여러 기기에서 동시에 주문하는 건 비정상적인 케이스다. 이 경우 1명만 성공하면 충분하고, 나머지는 실패 처리하면 된다.

여기서 핵심은 실패 이유를 구분해서 알려줘야 한다는 점이다. “이미 사용된 쿠폰”, “만료된 쿠폰”, “소유자 불일치” — 사용자에게 다른 메시지를 보여줘야 한다.

낙관적 락(@Version):

---
config:
theme: dark
handDrawn: true
---
sequenceDiagram
participant A as Transaction A
participant DB as Database
participant B as Transaction B

A->>DB: SELECT coupon (AVAILABLE, version=0)
B->>DB: SELECT coupon (AVAILABLE, version=0)
A->>DB: UPDATE SET status='USED' WHERE version=0
Note over A,DB: 성공! version 0 → 1
A->>DB: COMMIT
B->>DB: UPDATE SET status='USED' WHERE version=0
Note over B,DB: 실패! version already 1
Note over B: OptimisticLockException → 롤백
  • SELECT에서 먼저 읽으니까 상태를 확인할 수 있다
  • 이미 USED인지, 만료인지, 소유자가 다른지 구분 가능
  • UPDATE 시 version이 달라졌으면 실패 → “다른 곳에서 이미 사용됨”

Atomic Update라면?

UPDATE "issued_coupon"
   SET "status"='USED'
 WHERE "id" = ?
   AND "status" = 'AVAILABLE'
  • 영향받은 row가 0이면 실패인데, 왜 실패했는지 알 수 없다
  • 이미 사용됐는지, 만료됐는지, 소유자가 다른지 구분 불가

비관적 락은?

  • 가능하지만 불필요. 같은 쿠폰을 동시에 사용하는 건 비정상 케이스이므로 대기시킬 이유가 없다

그래서 쿠폰에는 낙관적 락을 선택했다. 동시성 테스트 결과: 10스레드 동시 사용 시 정확히 1건만 성공, 9건 실패.

좋아요 중복: 락이 필요 없다
#

좋아요는 (userId, productId) 조합이 유일해야 한다. 같은 사용자가 빠르게 두 번 탭하면?

DB에 UNIQUE(user_id, product_id) 제약이 걸려있다. 중복 INSERT를 시도하면 DB가 알아서 거부한다. 그리고 그 에러를 잡아서 정상 응답(멱등 처리)하면 끝이다.

try {
    productLikeRepository.save(productLike)
} catch (e: DataIntegrityViolationException) {
    // 이미 좋아요한 상태 — 정상 응답
}

여기에 비관적 락이나 낙관적 락을 거는 건 과잉이다. UNIQUE 제약이 원자적으로 중복을 막아주는데, 왜 추가 락이 필요한가?

like_count(좋아요 수)는 실시간 정합성이 필요한 값이 아니다. 스케줄러로 주기적으로 동기화하면 충분하다.

정리: 문제의 성격이 전략을 결정한다
#

문제성격전략핵심 판단
재고 차감가능한 한 전부 성공비관적 락대기 후 순차 처리, 재시도 불필요
쿠폰 이중 사용1명만 성공 + 실패 이유 필요낙관적 락선읽기로 상태 구분, version 충돌로 차단
좋아요 중복중복만 막으면 됨UNIQUE 제약락 자체가 불필요

“동시성 문제 = 비관적 락"이라는 공식은 없었다. 각 문제를 분리해서 보면:

  1. 동시 요청 시 기대 결과가 뭔가? (전부 성공 vs 1명만 성공 vs 중복 방지)
  2. 실패 시 사용자에게 뭘 알려줘야 하나? (실패 이유 구분 필요 여부)
  3. 재시도가 필요한가? (비관적은 대기, 낙관적은 실패+재시도)

이 세 질문에 답하면 전략이 자연스럽게 정해졌다.

배운 점
#

JVM Lock과 DB Lock은 같은 원리, 다른 레이어다. CAS는 @Version(낙관적 락)과, synchronized는 SELECT FOR UPDATE(비관적 락)와 대응된다. 근본 원리는 “읽기와 쓰기 사이에 다른 트랜잭션이 끼어드는 것을 막는다"로 동일하되, 적용되는 레이어가 다르다. synchronized + @Transactional이 안 되는 이유도 이 레이어 차이에서 온다.

트래픽 수준이 바뀌면 전략도 바뀌어야 한다. 10명이 주문하는 이커머스와 10만 명이 몰리는 선착순 이벤트는 같은 “재고 차감"이라도 다른 문제다. 비관적 락은 후자에서 병목이 된다. “이 전략이 맞냐"는 절대적 질문이 아니라, “이 트래픽에서 이 전략이 맞냐"가 더 정확한 질문이었다.

“어떤 락을 쓸까"보다 “이 문제의 성격이 뭔가"가 먼저다. 락은 도구일 뿐이고, 문제의 성격을 먼저 파악해야 적절한 도구를 고를 수 있다. 세 문제를 하나로 뭉뚱그려서 “동시성이니까 락 걸자"고 접근했다면, 좋아요에 불필요한 비관적 락을 걸고 있었을 것이다.
