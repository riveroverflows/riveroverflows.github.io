이 글에서 다루는 구현과 테스트는 Claude Code, Codex와 페어 프로그래밍으로 진행했다.

TL;DR
  • 주문 생성 트랜잭션 안에 재고, 쿠폰, 결제 관련 처리가 함께 들어가 있어 어디까지를 즉시 보장하고 어디서부터 후속 처리로 넘길지 기준이 불분명했다.
  • 그래서 주문 생성은 핵심 트랜잭션으로 두고, 후속 처리는 ApplicationEvent와 Kafka를 기준으로 나누어 처리하는 구조로 바꿨다.
  • Kafka 연동에는 Transactional Outbox를 적용해 이중 쓰기 문제를 피하고, event_handled와 paymentId 기준 중복 소비에 대응했다.
  • 선착순 쿠폰은 비동기 접수와 순차 소비 구조로 바꾸면서, 비동기 시스템에서는 브로커 연결보다 경계 설정과 실패 처리가 더 중요하다는 점을 확인했다.

시작하게 된 계기
#

이번 학습 라운드의 주제가 이벤트 기반 아키텍처와 Kafka였다.

동시접속 100만 명이 몰리는 콘서트 티켓팅 시스템은 어떻게 설계해야할까? 입구 트래픽 제어, 좌석 중복 방지, 결제 실패 시 좌석 반환 등등.. 그동안 혼자서 생각만 했었는데 이번 라운드 주제를 학습하면서 혼자서 구현해보면 재밌겠다는 생각이 들었다. 초장부터 김 새지만 아직 구현해보진 못했고 이번 라운드 과제 체크리스트를 충실히.. 수행했다. 학습한 내용으로 혼자서 티켓팅 시스템을 구현해볼 것을 다짐하며 과제를 시작했다.

이번 라운드 과제를 진행하기 전까지는 주문 생성 시 재고 차감, 쿠폰 사용, 결제 요청, 주문 저장을 전부 하나의 트랜잭션 안에서 처리하고 있었다.

@Transactional
fun create(command: OrderCreateCommand): OrderResult.Created {
    stockService.decrease(command.productId, command.quantity)
    couponService.use(command.couponId)
    paymentService.pay(command.paymentInfo)
    return orderRepository.save(Order.create(command))
}

PG가 느려지면 주문 전체가 느려지고, 쿠폰 서비스에 문제가 생기면 주문이 통째로 실패한다. 트랜잭션이 길어질수록 DB 락이 오래 유지되고 TPS가 떨어진다. 어디까지 성공했는지 알 수 없어서 복구도 어렵다.

이 구조를 바꿔야 했다.

핵심과 부가를 나누는 기준
#

트랜잭션을 나누려면 먼저 기준이 필요했다. “지금 꼭 해야 하는 것"과 “조금 나중에 해도 되는 것"을 구분하는 것이다.

구분하는 일트랜잭션 경계
핵심주문 생성, 금액 계산, 유효성 검증반드시 커밋 보장
후속쿠폰 차감, 포인트 적립, PG 호출커밋 이후 실행

PG 장애가 나더라도 주문은 저장되어야 한다. 쿠폰 차감이 실패해도 주문 자체가 롤백되면 안 된다.

여기서 이벤트라는 도구를 쓴다. Command는 “이걸 해라"라는 명령이고, Event는 “이런 일이 일어났다"라는 사실 통지다. 주문이 생성됐다는 사실을 알리면, 후속 처리를 담당하는 쪽에서 알아서 반응하는 구조다.

ApplicationEvent로 경계 나누기
#

Spring의 ApplicationEvent를 쓰면 외부 메시지 브로커 없이 후속 처리를 분리할 수 있다. 주문뿐만 아니라 좋아요, 상품 조회, 결제 콜백까지. 이벤트를 발행하는 쪽에서는 후속 처리를 몰라도 된다.

@Transactional
fun create(command: OrderCreateCommand): OrderResult.Created {
    val savedOrder = orderRepository.save(Order.create(command))
    eventPublisher.publishEvent(
        OrderCreatedEvent(
            orderId = savedOrder.id!!,
            userId = command.userId,
            productIds = command.items.map { it.productId },
        )
    )
    return OrderResult.Created.from(savedOrder)
}

주문을 저장하고 이벤트를 발행하면 끝이다. 후속 처리는 이벤트 리스너가 담당한다.

그런데 모든 이벤트를 AFTER_COMMIT으로 처리할 필요는 없었다. 좋아요나 주문처럼 데이터를 바꾸는 이벤트는 커밋이 확정된 후에 처리해야 하지만, 상품 상세 조회 같은 건 트랜잭션 결과와 상관없이 바로 기록해도 된다.

// 데이터를 변경하는 이벤트: 커밋 후에만 실행
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
fun handle(event: ProductLikeRegisteredEvent) { ... }

// 단순 조회 이벤트: 즉시 실행
@EventListener
fun handle(event: ProductDetailViewedEvent) { ... }

AFTER_COMMIT의 함정
#

좋아요 이벤트 리스너(ProductLikeEventListener)에서 AFTER_COMMIT 안에서 DB 작업을 했더니 예상대로 동작하지 않았다. 리뷰에서 post-commit 예외 격리가 부족하다는 피드백을 받고 나서야 원인을 알게 됐다.

트랜잭션은 이미 커밋됐지만 Spring의 트랜잭션 리소스가 아직 정리되지 않은 상태에서 리스너가 실행된다. 이 상태에서 Propagation.REQUIRED(기본값)로 새 트랜잭션 메서드를 호출하면, 이미 커밋된 트랜잭션에 참여하려다 DB 작업이 반영되지 않는다12.

실제 Outbox에서 이 문제를 해결한 코드를 보면 REQUIRES_NEW를 명시적으로 지정하고 있다.

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
fun handle(event: ProductDetailViewedEvent) {
    persist(topic = "catalog-events", eventKey = event.productId.toString(), ...)
}

@Async를 쓰면 잃는 것들
#

@Async를 붙이면 예외가 호출부로 전파되지 않는다. 리스너에서 PG 호출이 실패해도 사용자는 모른다. 로그를 남기지 않으면 장애가 조용히 묻힌다. MDC나 SecurityContext 같은 ThreadLocal 값도 비동기 스레드로 전파되지 않아서 TaskDecorator로 별도 처리가 필요하다3.

편한 대신 제어 흐름이 눈에서 사라진다. 이게 @Async의 대가다.

Kafka로 서비스 경계를 넘다
#

ApplicationEvent는 같은 JVM 안에서만 동작한다. 다른 서비스로 이벤트를 보내야 한다면 메시지 브로커가 필요하다.

멘토님이 이 구분을 짚어줬다. “Spring Event는 내부에서 핵심과 부가를 나누는 용도고, Kafka는 정산이나 쿠폰처럼 아예 다른 도메인으로 관심사를 넘기는 용도다.”

그래서 모든 이벤트를 Kafka로 보내는 게 아니라, 서비스 경계를 넘어야 하는 것만 골라서 승격시켰다.

이벤트토픽이유
ProductDetailViewedEventcatalog-eventsstreamer에서 조회수 집계
ProductLikeRegisteredEventcatalog-eventsstreamer에서 좋아요 수 집계
PaymentSucceededEventorder-eventsstreamer에서 판매량 집계
OrderCreatedEventinternal onlyAPI 내부 캐시 무효화 용도
PaymentFailedEventinternal onlyAPI 내부 로깅 용도

OrderCreatedEvent는 외부로 보낼 필요가 없었다. 캐시 무효화는 같은 JVM 안에서 끝나는 일이다.

Transactional Outbox Pattern
#

Kafka에 메시지를 보내는 것과 DB에 데이터를 저장하는 것은 서로 다른 시스템이다. DB 커밋은 성공했는데 Kafka 발행이 실패하면 데이터가 불일치한다. 이걸 이중 쓰기(Dual Write) 문제라고 한다.

Outbox 패턴은 이벤트를 Kafka에 직접 보내지 않고, 같은 DB 트랜잭션에서 Outbox 테이블에 기록한다. 별도 프로세스(relay)가 Outbox 테이블을 폴링해서 Kafka로 전송한다. 전송 실패 시 재시도하면 At Least Once 발행이 보장된다4.

다만 Outbox도 만능은 아니다. 멘토님 말로는 “폴링 프로세스가 죽으면 이벤트가 밀리고, 피크 타임에 데이터가 몰리면 폴링이 한계에 부딪힌다. 그래서 CDC(Debezium 같은)를 쓰기도 한다"고.

Kafka Config, 코딩보다 어려운 것
#

Kafka를 붙이는 것 자체는 어렵지 않았다. 진짜 어려운 건 Config였다.

spring:
  kafka:
    producer:
      acks: all                    # 모든 ISR이 확인해야 발행 성공
      properties:
        enable.idempotence: true   # Producer 멱등성 (PID + Sequence)
        min.insync.replicas: 2     # 최소 2개 ISR 보장
    consumer:
      auto-offset-reset: latest    # earliest로 하면 과거 데이터가 쏟아진다
      enable-auto-commit: false    # manual ack으로 처리 보장
      properties:
        max.poll.interval.ms: 300000

acks=all과 min.insync.replicas의 조합이 데이터 유실을 막는 핵심이다. Producer가 메시지를 보내면 최소 2개의 ISR(In-Sync Replica)이 확인해야 성공으로 간주한다5.

auto.offset.reset을 earliest로 설정하면 오프셋이 유실됐을 때 토픽의 처음부터 모든 메시지를 다시 읽는다. 운영 중에 이러면 엄청난 양의 과거 데이터가 한 번에 들어와서 장애로 이어질 수 있다.

max.poll.interval.ms를 초과하면 리밸런싱이 발생한다. Consumer가 메시지를 가져간 뒤 처리 시간이 이 값을 넘기면 브로커는 해당 Consumer가 죽었다고 판단하고 파티션을 다른 Consumer에게 재할당한다. 처리 중이던 메시지는 다른 Consumer에서 중복 처리될 수 있다.

멱등성, 설정 하나로는 부족하다
#

enable.idempotence=true를 켜면 Producer 측에서는 같은 메시지가 브로커에 중복 기록되는 것을 방지한다. 그런데 Consumer 측에서 같은 메시지를 두 번 처리하는 것은 막아주지 않는다6.

리밸런싱이 발생하거나 Consumer가 오프셋을 커밋하기 전에 재시작되면 이미 처리한 메시지를 다시 받을 수 있다. 이 중복 처리를 막는 건 결국 애플리케이션 몫이다.

event_handled 테이블에 처리한 이벤트 ID를 기록하고, 같은 ID가 들어오면 건너뛰는 패턴을 썼다. 여기에 추가로 판매량 집계에서 paymentId 기준으로 중복을 제거하도록 했다. eventId가 다른데 같은 결제에 대한 이벤트가 중복으로 들어오는 경우가 있었기 때문이다.

멘토님은 “이것만으로는 부족할 수 있다. 이전/이후 값을 비교하는 식으로 비즈니스 로직 수준에서 방어해야 할 때도 있다"고 했다.

선착순 쿠폰에 적용하기
#

선착순 100장 한정 쿠폰에 1만 명이 동시에 요청하면 어떻게 될까.

API는 발급 요청을 202 Accepted로 접수만 하고 바로 응답한다. 요청은 Outbox를 거쳐 Kafka coupon-issue-requests 토픽으로 들어가고, 별도 Consumer(commerce-streamer)가 순차 처리한다.

// API — 접수만 하고 즉시 응답
@PostMapping("/api/v1/coupons/{couponId}/issue")
fun issue(@PathVariable couponId: Long, ...): ResponseEntity<...> {
    val result = couponIssueUseCase.issue(command)
    return ResponseEntity.status(HttpStatus.ACCEPTED).body(...)
}

사용자는 발급 결과를 polling으로 확인한다. GET /api/v1/users/me/coupon-issue-requests/{requestId}를 호출하면 PENDING, ISSUED, FAILED 중 하나가 돌아온다.

Consumer 쪽에서 실제 발급 처리를 담당하는 핵심 로직은 이렇다.

@Transactional
fun handle(message: CouponIssueRequestedOutboxMessagePayload) {
    val request = couponIssueRequestRepository.findByIdForUpdate(message.requestId)
        ?: throw IllegalStateException("coupon issue request not found")

    if (request.status == ISSUED || request.status == FAILED) return

    val coupon = couponRepository.findByIdForUpdate(message.couponId)
        ?: run {
            couponIssueRequestRepository.save(request.markFailed("COUPON_NOT_FOUND"))
            return
        }

    if (coupon.isSoldOut()) {
        couponIssueRequestRepository.save(request.markFailed("COUPON_SOLD_OUT"))
        return
    }

    val issuedCoupon = issuedCouponRepository.save(
        IssuedCoupon.issue(couponId = message.couponId, userId = message.userId, ...)
    )
    couponRepository.save(coupon.issue())
    couponIssueRequestRepository.save(request.markIssued(issuedCoupon.id!!))
}

findByIdForUpdate로 쿠폰 row를 비관적 락으로 잡고, issueLimit과 현재 발급 수를 비교해서 SOLD_OUT을 판정한다. 중복 발급은 issued_coupon(coupon_id, user_id) unique constraint가 DB 수준에서 막는다. 같은 사용자가 같은 쿠폰을 두 번 요청하면, 이미 발급된 쿠폰을 찾아서 기존 request를 재사용한다.

실패 유형도 구분했다. COUPON_NOT_FOUND, COUPON_DELETED, COUPON_EXPIRED, COUPON_SOLD_OUT은 terminal failure다. 재시도해도 결과가 바뀌지 않으니 ack를 보내서 다음 메시지로 넘긴다. 반면 DB 연결 실패, 타임아웃 같은 인프라 장애는 일시적인 문제다. ack를 보내지 않으면 Kafka가 같은 메시지를 다시 전달한다. 이 구분이 없으면 비즈니스 실패를 무한 재시도하거나, 일시적 장애에서 메시지를 영구 유실할 수 있다.

나는 Redis 없이 DB 비관적 락 + unique constraint로 풀었다. 올리브영이나 토스 같은 곳은 Redis 원자적 연산이나 RedLock + Kafka Throttling 조합으로 훨씬 큰 트래픽을 처리한다고 한다78. 멘토님이 EDA로의 사고방식 전환이 중요하다고 했던 말이 조금 와닿았다. 지금은 DB 락으로 충분하지만, 규모가 커지면 Redis를 앞에 두는 것을 고려해보면 좋을 것 같다.

마무리하며
#

이벤트로 분리하면 코드는 깔끔해진다. 대신 예외가 조용히 묻히고, 중복 처리가 생기고, Config 하나 잘못 건드리면 장애가 난다. 비동기 시스템은 만들기보다 운영이 어렵다는 걸, 이번 라운드를 하면서 계속 느꼈다.

그래도 얻은 게 있다. 어떤 이벤트를 AFTER_COMMIT으로 처리하고 어떤 걸 즉시 실행할지, 어떤 이벤트를 Kafka로 승격하고 어떤 걸 내부에 남길지 — 이런 경계를 나누는 감각이 생겼다. enable.idempotence=true만으로는 부족하다는 것도, Config 한 줄이 장애로 이어질 수 있다는 것도 직접 겪어야 알 수 있었다.

글 초반에 언급한 “동시접속 100만 명이 몰리는 콘서트 티켓팅 시스템은 어떻게 설계해야할까?” 질문으로 돌아가서.. 이번에 다룬 이벤트 분리와 Kafka 파이프라인 만으로는 동시접속 100만 명을 감당해 내기는 어려울 것 같지만 우선 배운 것 만으로 구현해보는 것도 좋을 것 같다. 입구 트래픽 제어나 대기열 시스템 같은 기술을 도입하고, 큰 기업에서 적용한 기술을 같이 도입해보면 좋을텐데 이 영역은 아직 잘 모르는 부분이라, 학습 후에 다시 다뤄봐야겠다.

직접 해봐야 확실히 알 게 된다는 게 요즘 들어 정말 많이 느껴진다.. 백견이 불여일타!
