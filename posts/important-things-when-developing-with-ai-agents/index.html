왜 갈피를 못 잡았는지부터 생각해봤다
#

이번 주 주제는 Agents & TDD였다. 사실 시작할 때부터 방향이 흔들렸다.

  • AI랑 같이 코딩하는 데 집중해야 하는지
  • TDD와 코틀린 학습에 집중해야 하는지

그래서 일단.. 이전 회사에서의 경험에서 비롯된 “AI가 참고할 문서를 잘 만들어야 한다"는 생각으로 문서 작성에 시간을 많이 썼다.

그렇게 4일이 지나 멘토링 시간이 되었는데도 나는 기능 구현을 거의 못한 상태였다.

“본질에서 벗어난 것 같은데, 나만 다른 방향으로 가고 있는 것 같은데.. 문서 작성 계속 해야되나.. 일단 구현부터 해봐야되나..” 머릿속이 복잡했다.

멘토링에서 받은 답변이 전환점이 됐다
#

멘토링 때 아래와 비슷한 질문을 했다.

요구사항이 잘 작성돼 있으면 구현은 AI가 빠르게 해주는데, 문서 작성에 시간을 너무 많이 쓰고 있는 것 같습니다. 이번 주 학습의 본질에 제대로 집중하지 못한 것 같은데, 앞으로 어떤 방향으로 학습해야할까요?

지금 다시 보니까 이미 답을 알고있는데 질문한 것 같네..

답변은 명확했다.

“이제는 문서를 잘 작성하는 능력이 중요하다. 그 문서가 AI에게는 작업 지시서가 되기 때문이다.”

이 말을 듣고 오히려 마음이 가벼워졌다. 내가 했던 작업이 완전히 빗나간 건 아니라는 걸 확인했기 때문이다. 어쩌면 듣고 싶은 말을 들어서일수도?

교육 과정의 목표에 대해서 다시 생각해봤다.
#

멘토링 이후에 “이 교육 과정의 핵심 목표가 뭘까"를 다시 생각해봤다..가 기억이 안나서 홈페이지를 다시 확인했다.

왜 그렇게 판단했는지 설명할 수 있어야 한다.

요즘은 AI가 찍어내는 방대한 양의 코드를 많이 사람이 하나하나 확인하기 어렵다보니 무지성 승인되는 코드가 쌓이기 쉽다. 여기서 비롯된 코드의 문제는.. 처음엔 괜찮아보이다가도 결국 터져버린다.(어떻게 아냐구요? 저도 알고 싶지 않았어요ㅠ)

결국 AI와 같이 개발하는 시대에 중요한 건 이해하지 못하는 코드를 마구 찍어내면서 일주일 걸릴 일을 하루만에 끝내는 것도 아니고, 일단 어떻게든 돌아가게만 구현한 것끼리 뭉쳐서 빛 좋은 개살구 토이 프로젝트를 만드는 것도 아니다.

내가 생각했을 때 중요한 건.. 구현 속도는 AI를 따라잡을 수 없으니 내가 가스라이팅 하는대로 AI가 잘 움직일 수 있도록 계획을 잘 작성해야 하는데, 관련된 지식이 없으면 내가 역으로 가스라이팅 당할 수 있으니 필요한 지식을 학습해야한다는 것이다.

그래도.. 시작은 역시 어려웠다.. 그래서 흐름을 정리해봤다!
#

마음은 홀가분해졌지만 아쉽게도 머리는 아직 정리가 안됐는지 손이 바로 움직이지는 않았다.. 나는 시작 전에 머릿속에 흐름이 어느 정도 그려져야 실행에 옮길 수 편이라 무엇을 먼저 할지부터 다시 정리했다.

  • 이번에 해결할 기능 1개
  • 검증할 실패 케이스 1~2개
  • 완료 기준(어떤 테스트가 통과하면 끝인지)

일단 작은 단위로 정해두고 시작하니까 그제서야 작업이 조금씩 진행됐다. (막상 시작하니까 역시나 저거보다 훨씬 많이하게됨ㅎ)

이번주에 느꼈던.. agent랑 개발할 때 생각했던 것보다 더 중요한 점
#

1. 명확한 지시가 필요하다.
#

당연한 말이다. 머리로는 알고 있는데 귀찮은 마음이 앞섰고 내가 agent의 입장이 되어보지 못해서 대충 넘겼을지도 모른다.

생각해보니까 agent의 입장이 되어 본적이 있구나. 일할 때 요구사항 제대로 안주면 열 받아하면서 agent한테는 왜 그렇게 요청했나 모르겠다. 그 때는.. 한국어로 편하게 개발할 수 있다는 바이브코딩 뽕에 취했있던 것 같다.

어쨌든 목표가 모호하면 문서든 코드든 계획이든 시간을 엄청 들이는데에 비해 눈에 보이는 결과를 쌓지 못했다.

2. AI는 더 명확한 지시가 필요하다
#

AI는 실행 속도는 빠르지만 내가 원하는 방향을 AI가 알아서 찾아가진 않는다. 내 지시가 모호하면 결과도 모호해졌다.

나에게는 요청을 작게 쪼개는 방식이 효과적이었다.

  1. 실패 테스트 하나 작성
  2. 그 테스트를 통과하는 최소 구현
  3. 필요한 리팩토링만 적용

3. 가스라이팅을 잘하려면 내가 어떤 도구가 필요한지는 알아야 한다
#

“이 방식으로 가자"라고 말하려면 비교 대상이 필요하다

  • Mock vs Fake
  • 도메인 규칙 테스트 먼저 vs 서비스 흐름 테스트 먼저
  • 지금 리팩토링할지, 다음 루프로 넘길지

후보를 세우고 고르려면 각각을 어느 정도는 알아야 했다. 결국 학습이 필요한 이유도 여기서 분명해졌다.

4. 최종 책임은 사람에게 있다. 아직까진..
#

아직은(..) 개발자라면 AI가 만든 코드를 보고 “왜 이렇게 구현했는지” 설명할 수 있어야 한다. 계획을 열심히 세우더라도 세상에 완벽한 계획은 없기 때문에 늘 그렇듯 계획은 틀어지기 마련이다. LLM Agent는 내가 생각해둔 것들을 빠르게 실현시켜주는 도구로 설명할 수 없으면 유지보수도, 확장도 어렵다.

이번 과제를 하면서 느낀 건, Agent를 잘 쓰는 사람은 프롬프트를 멋지게 쓰는 사람이라기보다 판단 기준을 분명히 갖고 있는 사람이라는 점이었다.

이번 주를 정리해보면..
#

진짜 오랜만에 시간이 엄청 빨리간 것 같다고 느꼈다. AI한테 잘 지시하는 것과는 별개로 일단 뭐라도 시작해야된다고 다시 한번 느꼈다..ㅠ AI Agent와 TDD를 어떤 방식으로 학습해야 하는지 기준을 세운 주간이었다.

  • 문서 작성은 낭비가 아니라 지시 품질을 높이는 작업
  • 작업 단위를 작게 나누는 습관이 품질에 직접 영향
  • “왜 그렇게 판단했는지"를 설명하는 능력이 핵심
